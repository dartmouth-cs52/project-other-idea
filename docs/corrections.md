# Correcting Haptic

What a company sees about where Haptic falls short, and what it can change about how Haptic guides, from the dashboard and without waiting for us: corrections, routes it teaches Haptic by doing the task, and controls never to point at. For the project overview, see the [README](../README.md).

## What people can't find, and guide health

The dashboard leads with what people can't find: each group ranked by how many different people asked, with how many got there, where most of the rest stopped, and its guides one click away. Guide health follows: how often each common group's guides finish, week by week. A group whose finish rate this week is at least 20 points below the three weeks before, with at least five guides in each, is flagged, with the step and page where its guides now stop and the control earlier finished guides pointed at there that no guide has this week. That is what a change to the product looks like from here. Once a day the website's Worker emails the company's people about each flagged group that at least five people asked before, at most once a fortnight per group (`web/worker/health.ts`, `health_alerts`). A first answer the visitor read without clicking counts as getting there, since Haptic showed them where it was.

Questions are grouped by meaning with plain text rules, never a model: the question's words without filler like "how do I", with a plural s taken off, in order, so "How do I export invoices?" and "export my invoices" are both "export invoice" (`src/shared/questions.ts`, and the same function in SQL in `db/migrations/0011`, kept as a generated column on `guides`). Each guide keeps a hash of the widget's random id made with the site's id, so the dashboard counts people and not questions.

## Point here instead

When Haptic points at the wrong thing, the company fixes it from the dashboard without waiting for us. On any step of any guide, "Point here instead" picks the control it should have pointed at, from the controls known on that page (the crawl's, and those enough visitors have seen) or by typing its label. Element ids only last for one snapshot, so a correction is kept by page, role and visible label, with the question it was made for (`src/shared/corrections.ts`). Each step's prompt gets the corrections for questions like the one asked and for the page the visitor is on, at most five, after the page and before the question. A site without corrections is asked exactly as before, and corrections never change the cached part of the prompt.

## Teach Haptic

When Haptic got a question wrong, someone at the company shows it the right way by doing the task in their own app, and Haptic guides that way from then on (`src/shared/teach.ts`). There is no screen recording: the script already on the page records which controls are used, which gives the exact control, keeps out everything else on screen, and is already in the form a guide needs.

1. **Start.** "Teach Haptic the right way" is on a failed guide's drawer and on each row of "What people can't find", and "Teach Haptic a task" under How Haptic guides here takes a question. Each makes a teach session (`teach_sessions`, `db/migrations/0014`): a random 32-byte token, of which only the SHA-256 is kept, the site, the question, who started it, and 30 minutes to open it in (`web/worker/teach.ts`). The dashboard opens the site in a new tab with the token in the address's fragment, `#haptic-teach=<token>`, which browsers never send to the site's server, so it is in no log of theirs. A failed guide's tab opens on the page that guide started on, when that page has no record's id in it.
2. **Teach mode.** The widget takes the token out of the address bar at once and claims it from the widget server (`POST /v1/teach/claim`, `src/server/teach.ts`) with a random secret of its own. Only an unexpired, unclaimed token made for this site, from an address the site allows, is accepted, and only once: from then on only the token and that secret together reach the session, so the link cannot be reused in another tab or by anyone else. A claimed session has 30 minutes. The widget then starts no guide, asks the model nothing and acts on nothing; it shows a bar, "Teaching Haptic: <question>. Do the task as a visitor would. Haptic records which controls you use, not what you type.", with Done, Undo last and Cancel (`src/widget/teach.ts`). A link that cannot be used says why on the page, for example "This teaching link has expired. Start again from your Haptic dashboard.", and the widget then starts as usual. Each caller gets 20 teach calls a minute (`TEACH_LIMIT`).
3. **Recording.** Each step is the control as the page reading names it (its kind, its label and the section it sits in, with the same masking as everything the widget sends), the page as a path with ids masked (`/budgets/:id`), and what was done with it: pressed, chose X in a list, typed in field F, ticked, pressed Enter. What is typed is never read. A press and the choice it opened become one step ("Choose Marketing in Department"), a control in a table's row keeps its name only when other rows have one of the same name (Edit, never the record's own name), and a control with no name is still a step, so nothing the person did is dropped without a word. The steps are kept in the tab's `sessionStorage`, so they survive page loads and route changes, until the server has them.
4. **Review and save.** Done posts the steps (`POST /v1/teach/done`). The server checks and masks them again, and marks each step whose words say it saves, sends, pays or deletes as one that commits, by the same word lists Do it with me uses. The dashboard shows them as a numbered list in plain words ("On /budgets, press New budget"), where the person deletes steps, adds a one-line note to any of them, names a control the recorder could not ("an unnamed control on /budgets", which has to be named or deleted before saving), and marks the last step "leave this click for the visitor". A step that commits is always left for the visitor. Saving keeps the route in the site's context (`taught`), beside the corrections, replacing an earlier route for the same question. A send or a save that fails says so, with Retry, and the steps are kept until they are saved. A session nobody saves is deleted a week after it was made.
5. **Guiding.** A visitor's question like the one taught (matched the way corrections are, `similarQuestion`) carries the route in the step's prompt as the company's own instructions: the steps in order with page and control names, notes, and which click is the visitor's. The model still checks each step against the page it sees, so a control that moved or reads a little differently does not break it. Other questions are asked exactly as before, and the cached part of the prompt never changes. In Do it with me the route may be followed, but the labels of the steps it leaves for the visitor count as the site's commit words for that question, so the server never lets Haptic press them.

`npm run site:publish` keeps taught routes when it replaces the rest of a site's context.

## Controls never to point at

A company lists controls Haptic must never point at, like "Delete workspace" or "Transfer ownership". The list goes in the site's prompt, and it is enforced in code twice: the server replaces any reply that points at one, and never sends one as the early pointer, and the widget checks every pointer against the list again before it moves. Either way the visitor reads "I can't help with that here." and the guide ends as `blocked`. Both lists are kept in the site's context, so the widget server reads them with the site and a change reaches visitors within a minute. `npm run site:publish` keeps both lists when it replaces the rest of a site's context.

The benchmark has cases for both: see [`eval/README.md`](../eval/README.md#corrections-and-controls-never-to-point-at).
