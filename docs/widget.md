# How the widget follows a page

The widget runs on pages it doesn't control. This covers how it keeps up with them: how it reads a page and hears what the visitor does, its chat and the glow that shows it is thinking, dialogs, controls something else covers, single-page apps that change the address, Do it with me, what it learns about a site from visits, what it leaves running, and how to test it in real browsers. For the project overview, see the [README](../README.md).

## Reading the page and hearing the visitor

The page is read in one pass (`src/widget/snapshot.ts`): every control with its role, label and state, the headings, and short pieces of visible text, including table rows, menus and lists a page draws itself, controls inside open shadow roots and same-origin frames, controls that show only while the mouse is over them, and sign-in walls. Nothing typed is read: not a field's value, and nothing inside an area a visitor writes in, which is listed as one control and not looked into. What the visitor then does is heard as they do it (`src/widget/observe.ts`): a click, typing in a field, a pick from a list the control opened, a key the sentence asked for, a page load. After the step the model called the last, the widget looks once more at what came of it (a closing question), so a guide does not end on a click nobody checked.

A field is filled in when typing in it pauses for 1.2 seconds, when Enter is pressed in it, or when the visitor goes on to another control before the pause: typing a first name and clicking Last name straight after is "filled in First name, then clicked "Last name"", not a wrong click. A click on a button or a link before anything is typed in the pointed field is still a wrong click, at once. A click into another field is not, yet: clicking into a field is not using it. Typing there is the wrong field, heard at the first letter. Picking one of the browser's suggestions there is the step when the autofill fills the pointed field too, as Chrome's does: it fills the field it was started from first, then the rest of the form. If it fills that field and not the pointed one, it is the wrong field a quarter of a second later (`AUTOFILL_DONE_MS`). The browser's own autofill is heard as soon as it lands, with no pause to wait for: the field is in the `:autofill` state as its input event arrives, and the event is not one of typing (Chrome sends a plain `Event`, Firefox an `InputEvent` that replaces the text). The model is told the browser's autofill did it, and may have filled in other fields of the form, so it does not ask for those again. Before this, a visitor on the request access form who picked one of Chrome's suggestions in First name, which filled in First name and Last name at once, and clicked Additional details straight after, was told "Not that one". `test/browser/autofill.test.ts` drives Chrome's real autofill through the DevTools protocol (`Autofill.trigger`), so the events are the ones Chrome sends: a focus, a keydown with no key, an input, a change, a keyup and a blur on each field, and no `focusout`.

When the control the pointer is on goes without being used, because the visitor closed the dialog or menu it was in, filtered the list it was in, or the page drew its list again without it, or a modal the page opened by itself shuts it out, the widget notices within half a second. The pointer and its sentence go at once, nothing is left over where the control was, and the next step is asked for from the page as it is now, with what happened in plain words: "The user clicked outside the dialog "Pay Linden Logistics", which closed it without using button "Continue"." (`vanished` in `src/widget/guide.ts`). A control the page only drew again, on a new node, is pointed at again with no question; one whose dialog or menu closed is not looked for, since a control like it elsewhere on the page is not it. A page that keeps taking the pointed control away, or covering it, is asked about three times in thirty seconds. The fourth time the guide stops with "This page keeps taking away what I point at, so I've stopped for now. Ask again once it settles." and is reported as a loop (`MAX_GONE`), so such a page cannot run a guide through all its twenty steps by itself. Being drawn again does not count. A row's action that shows only while the mouse is over its row, whether the control or the cell around it is see-through, is listed as "shows on hover" and the model says to move over the row. The ring shows where it will appear, and Haptic never clicks or focuses it to make it show: focusing would move the visitor's keyboard and can set off the page's own focus handlers, and many pages show such actions only on hover.

How a guide's ending is reported: the moment the last pointer of a guide that got there shows, and the moment the visitor uses the last control, the outcome is sent at once, with `keepalive`, since the page may be about to go. While a pointer the model called the last is on show and the visitor has not used it, a `pagehide` listener reports it as shown if the tab closes. The guide keeps its id for the look that follows, and nothing is reported twice; the server keeps the first outcome it hears, and keeps "finished" only when the steps it recorded bear it out (see [which guides are finished](operations.md#which-guides-are-finished)). Each ending names the step whose reply it rests on, counting from 0, so the server judges that step and not the look that follows it.

## The chat

The chat is the one in the home page's demo (`web/components/demo/kit.tsx`), drawn by `src/widget/ui.ts`. It stays open from the question to the last step. The question is a bubble at the top. One line under it says what Haptic is doing: "Thinking" with a lighter shade sweeping across it while the widget waits for the model, and "Showing you how" with the pointer's mark while it shows a step. The ask box stays where it is, and for as long as a guide runs its button is the stop button. Once anything is in the chat, a turning arrow on the left of the ask box's row starts over: it stops a guide that is running and clears the chat back to an empty ask box. Under the ask box, always, is the line that says Haptic is an AI and can be wrong. A small × in the chat's top right corner closes it, as the launcher's second click and Escape do: a visitor who opened it by mistake has an obvious way out. It only puts the chat away. A guide that is running carries on, its caption's × is what stops it, and the launcher brings the chat back as it was.

**The pointer.** The ring around the control is the accent with a white edge on both sides and a soft shadow, and it and the caption show as the pointer lands. A click on the control is answered with a press: the ring and the pointer dip and come back in a quarter of a second, where they are, even if the click took the control off the page, and then go. Filling in a field, or clicking something else, gets no press.

**Never on top of the control.** When the chat would cover the control being pointed at, it moves up the right side of the window while the pointer is there, and comes back down when it has gone (see the launcher's place, below). It does not move for the caption when the caption can move instead.

**Scrolled out of the window.** The pointer, the ring and the caption are drawn over the window, not the page, so they follow the control every frame. When the visitor scrolls the control out of the window, the ring and the pointer go, and the caption waits at the edge of the window the control went off, top or bottom, led by an arrow button that scrolls the control back into view. Nothing is left pointing at whatever scrolled under where the control was. Once the control is back in the window, the pointer, the ring and the caption go back round it. A control the guide pointed at while it was out of the window is given a second and a half for the guide's own scroll to bring it in, and nothing of ours shows meanwhile. While Haptic acts, the point it is about to press stays where it is (`offView` in `src/widget/ui.ts`, `test/widget/scrolling.test.ts`).

**How it ends.** The green tick and "Done" show under the question when the guide's ending is `finished`: the visitor followed it to the end, which is the same ending that is billed. An answer in words, a control that was shown and not used, and a sentence that says Haptic can't help end without it. The sentence that ends a guide stays in a caption just above the chat until its × puts it away. "Did this help?" follows, and the answer is posted to `/v1/guides/<id>/report` and kept on the guide (`guides.helped`), where the dashboard counts it.

**The thinking glow.** Thinking shows on the page, not in the chat, and only for as long as the widget is waiting for the model (the guide's state is `asking`). A soft band the width of the page comes in at the top edge and falls towards the bottom, once for each wait. How long a wait will be is not known, so the band is paced to it: one transition of eight seconds that is quick at first and slower all the time (`FALL_MS` and `FALL_EASE`), which puts its middle at the top edge after 0.4 seconds, halfway down after 1.2, a typical wait, and four fifths down after 3, and never at the bottom. The moment the reply arrives a second transition takes it from wherever it is on to the bottom and off the page in 0.45 seconds, fading, and its element is then not displayed. So every wait is one pass from top to bottom, whatever its length. A reply that says something went wrong, and a guide that was stopped, end it the same way.

It is drawn by an element of its own, `<haptic-veil>`, put in the page once, when the widget starts, and never moved. It is in the top layer just under `<haptic-root>`, shown again whenever ours is, so the chat, the pointer, the ring and the caption are over it and are never tinted, and it is over a dialog the page has opened. Being a separate element is what lets it be blended into the page: multiplied into a light page, so the page's words stay dark and sharp through it, and screened into a dark one, going by the backgrounds behind three spots on the page. It takes no clicks, and the page's reading skips it (`data-haptic-ignore`). It is not displayed at all unless a glow is on, and that is switched in its own stylesheet, so nothing on the page changes and the widget's own watching of the page hears nothing.

The band is one element with one gradient and one mask, and only its transform changes. The gradient runs through three fixed colours (`GLOW` in `src/widget/ui.ts`): Haptic's blue, #1E6EF4, and its neighbour on either side, the same as the home page draws and the same on every site, whatever its accent. They are mixed in OKLCH so there is no seam between them. The pointer and the ring keep the site's accent. The mask is a bell spelled out in eleven stops, since a gradient only joins its stops with straight lines and a bell is what stops the band reading as a stripe. A browser with no masks shows no glow. With reduced motion on there is no glow, no shimmer and no press. `test/browser/chat.test.ts` covers all of this.

**What the glow costs.** The blend is the costly part, not the mask or the gradient: the browser has to read back what it has drawn of the page and mix the band into it, over the whole window, for every frame the band moves. Where a graphics card does that, no frame was lost in any measurement here. Where there is none (a virtual desktop, a browser with its graphics card turned off, a CI runner), it is done on the processor. With the browser held to one core and the processor slowed four times, one frame in twenty took 33 to 50 ms while the glow was on, against 17 ms with the blend taken out, and 17 ms with no glow. Taking the mask out changed nothing. So on such a machine the page runs at about half its frame rate while Haptic thinks and for the 0.45 seconds the band takes to leave, which is when the pointer starts its glide. Nothing waits on a frame because of it: the ring is placed when the widget points (`pointAt`), not at the next frame, and the test that delays every frame by a third of a second holds that. A phone was not measured.

## Modal dialogs

A page's modal `<dialog>` makes everything outside it inert, Haptic's own element included. The widget moves its element into the open dialog the moment it opens, shows it again on top, and moves it back out when the dialog closes, so the pointer and the Stop button keep working through nested dialogs too. Escape in Haptic's ask box closes Haptic's panel and not the page's dialog.

## Covered controls

A control on screen that something else covers, like a button under a stack of cards or the page behind a full-screen overlay, is left out of the snapshot, because a visitor can't click it. The browser's own hit test decides, at the control's middle, then around it, then at the middle of each line of a control that wraps (`keepReachable` in `src/widget/snapshot.ts`). A control only scrolled out of its scroll box stays in and is said to be above or below, and so does one under a sticky header or a bar pinned to the window, since pointing scrolls it into view. One under a list, a menu or a box the page opened over it stays too: it is only under it while that is open. A see-through field drawn by a box around it, like a styled tick box, counts as that box, and a layer over the whole window, like a wall of cookie choices, is then all of the page that can be used.

## Route changes

Single-page apps change the address without loading a page, so the widget watches for it itself: through the browser's Navigation API, or by looking at the address every tenth of a second in a browser without it, and never by changing the page's own `history` (`src/widget/navigation.ts`). If the address changes while the model is answering, the answer is about a page the visitor has left, like the page they were on when they clicked something that took a moment to load. The widget hangs up at once and asks again from the new page, and the server stops the model call and counts the dropped step on the guide (`cancelled_steps`). An app that changes the address first and draws the page a moment later is waited for: a new address over the same controls as before has not been drawn yet.

## Do it with me

Off unless the company turns it on for its site (`npm run tag -- acting <site id> on`, then publish; `acting.paths` limits it to parts of the product, and `commitWords`, `maxActions` and `confirmFirst` tune it). A page can turn it off for itself with `data-acting="off"` on the script tag, never on. The ask box then has a Do it button beside Send. Do it or Send pressed with nothing typed asks nothing: a line under the ask box says what to type, and the keyboard goes into the box. Haptic clicks, types and chooses on the page while the visitor watches (`src/widget/act.ts`), and every action first passes the gate (`src/widget/gate.ts`): it leaves to the visitor anything whose name, address or script says it saves, sends, pays or deletes, never types passwords or payment details, and types only what the visitor wrote in their question. What it cannot tell from those is said below. A link is judged as a button is, by its words and by where it leads ("/expenses/7/approve" approves). Only a link that visits another page of the site and whose words and address commit nothing is pressed for what it is, and every link press is watched: a page that answers it by sending something to its server stops acting at once. One kind of link is named for what its form will do, like "Issue card" leading to "/cards/new". Such a link is pressed when it is a real visit (an `<a href>` with no script written on it) whose address ends in the word frameworks give the page that holds a form ("new", "edit" or "compose") and carries no commit word elsewhere. "create" and "add" are not such words: "/wishlist/42/add" is as often the act itself, done by the visit. Its own words then stop it only when they delete, pay, sign in or out, take data out or reveal. "#", `role="link"`, a link with a script written on it (an `onclick`), and addresses like "/invites/send" stay the visitor's. The gate sees a script only when it is written on the link. One added with `addEventListener`, one a parent listens with, or React's is not seen (React leaves an empty `onclick` on every element it handles, which counts as none). So a link to a form page whose hidden script sends something in place of the visit is pressed once: the tripwire sees that request, acting stops there, and the visitor is told to check that nothing was saved. A visit that commits on the server by being loaded, a plain GET to an address ending in "new" or "edit", is a page load like any other and cannot be seen. The server checks every reply with the same rules (`src/shared/act-rules.ts`) before the widget sees it. At the last control, the one that commits, it points and hands over: the visitor makes that click. The visitor's own click or key pauses it, Escape stops it, Back ends it, and the panel lists what it did. To check that its own typing took, it reads that field's value inside the browser, and never sends it. Dates are not picked in this version. Answers is never used for a step Haptic was asked to do. The code that acts, with the gate and the word tables, is a second file, `widget-act.js`, served beside `widget.js` by the same server (`src/widget/acting-code.ts`). Only a site with acting on loads it, as the widget starts, so most pages never fetch it, and a policy that allows Haptic's script allows it too (a policy that names the one file `widget.js`, rather than Haptic's address, would need the second file named as well). If it does not come, the site is guided by pointer, and Do it is not shown.

## Teach mode

A link from the dashboard's "Teach Haptic" opens the site with `#haptic-teach=<token>` in the address. The widget takes it out of the address bar before it does anything else, and only a token the widget server accepts starts teach mode (see [Teach Haptic](corrections.md#teach-haptic)). Teach mode is a file of its own, `widget-teach.js` (about 22 KB, 8 KB gzipped), that the widget loads from beside itself only for a teaching link or a teaching session the tab already holds (`src/widget/teach-code.ts`), the way it loads the code that acts; the build fails if `widget.js` holds teach mode, or `widget-teach.js` its own copy of what it takes from the first file. If the file cannot be loaded, the page says so. Then no guide starts, nothing is learned from the page, and no model is asked. A bar sits at the bottom of the window (Done, Undo last, Cancel, and an arrow that moves it to the top), in the top layer and inside the page's own modal dialog while one is open, so it can always be pressed. Listeners on the window, in the capture phase and passive, note each press (read when the pointer goes down, before the page reacts), each field typed in (once per field, never its value), each choice in a native list, and Enter in a field (`src/widget/teach.ts`). Each is named from the same page reading a guide uses, with the bar left out. A name teach mode reads for itself, of a group of options, a list or a control the reading leaves out, is read with what the fields hold in hand (`withTyping` in `src/widget/snapshot.ts`), and every step's names go through that filter again as it is recorded, so words that repeat what a field holds are `[typed]`, as in what a guide sends. The steps are kept in `sessionStorage` until the server has them. While teach mode runs, the widget never calls `preventDefault` and never acts on the page. Like the chat, the bar and a teaching link's notice are left to right on a page written right to left, and only the question the bar was opened for reads in its own direction (`dir="auto"`).

## Learning the site from visits

The crawl builds the first map of a site, but it can't sign in, and it can't open what only a click reveals. So the widget also sends an outline of each page it loads on, once per page per tab, when the page has settled and the browser is idle (`src/widget/learn.ts`): the title, headings, and the labels of its links and buttons, with an icon-only button named by its icon, like `icon:share-2`. When a click is followed by a new page within eight seconds, it sends the clicked label as a link on the page the click came from, like "View, in a dialog → /set/:id", which is how Haptic learns a page that only a dialog leads to. Labels only: never what is typed into a field, never what is in a table's cells, and a label holding an email address or a long number is dropped whole.

Each label is counted by distinct visitor (`src/server/learned.ts`). The widget keeps a random id in the site's `localStorage`, and the server keeps only a hash of it made with the site's id, up to ten per label, in `outline_labels`. A browser that keeps no storage has no id, and what it sends is not used. A label reaches the prompt only once enough different visitors have seen it: 3 online, 1 on your own machine, or `HAPTIC_LABEL_THRESHOLD`. That keeps one person's own data, like the name of their project, out of everyone's prompt. What is learned is merged with the crawl's pages when a site is read from the database, so a step never waits on it. The crawl's pages come first, pages only traffic knows follow, navigation that is on most pages is listed once, and each page lists at most 24 buttons. Learned labels are listed in a fixed order, so a count going up does not change the prompt the model provider keeps cached. A site whose context has `"learn": false` sends no outlines.

**What an outline can't do.** Anyone can post an outline, not only the widget: a site's id is in its script tag, and the visitor id is whatever the caller says it is. So:

- A label is never learned if it holds an angle bracket (or the small and full-width forms of one), a control character, or an invisible character other than those real text is written with (the soft hyphen, the zero-width space and joiners, and the marks that set one character's direction). Nor is a page or a link address that a browser would not send as it is: one with a space, a quote or an angle bracket in it. The widget leaves such a label out before sending, and the server checks again, with the same function (`isLearnableLabel` and `isLearnableRoute` in `src/shared/types.ts`). A label like "Next >" is dropped whole rather than cut down, since what would be left is not what the page says.
- The site map is written into the prompt with anything shaped like a tag defused, `</site_map>` becoming `</ site_map>` (`inert` in `src/server/prompt.ts`), whether it came from the crawl or was stored before these checks. The same goes for what a closed control is known to open, in the page block. The prompt's rules already say that everything in `<site_map>` is data and never instructions.
- `/v1/outline` takes no request without an `Origin` header, unlike the other addresses. A browser names the page's origin on every POST the widget makes, to another origin or its own.
- A label is also counted by the network each caller's address belongs to, which a caller cannot make up: an IPv4 address whole, and the first three groups (the /48) of an IPv6 one, which is as much as one subscriber is given. The server keeps only the first two bytes of a hash of it made with the site's id, up to ten per label. About 65,000 IPv4 addresses share each value, so it can't be turned back into an address, and it still tells three networks apart. A label reaches the prompt only once its visitors called from enough different networks: 3 online, none needed on your own machine, or `HAPTIC_NETWORK_THRESHOLD` (never more than the visitors needed). On the Worker the address is Cloudflare's `CF-Connecting-IP`; on the Node server it is the socket's, so behind a proxy every caller is one network.

That makes three made-up ids from one machine one network, and learns nothing. It does not make a label true: callers on three networks, which can be rented cheaply, can still add a plausible button that isn't there, or a sentence of up to 60 letters. They can no longer put it anywhere but in the site map, among the labels. The cost falls on products whose visitors all share one network, like an internal tool used from one office behind one address: online they learn nothing from visits, and `HAPTIC_NETWORK_THRESHOLD=0` turns the network count off for that server, along with what it protects against. Labels kept before networks were counted (before `db/migrations/0014`) have none, so each has to be seen from three networks again before the prompt gets it back. It keeps the visitors it had.

**How much is kept.** A site keeps at most 5,000 learned labels and 5,000 items behind controls. Past that, new ones still go in, and room is made by dropping others: never the ones the prompt reads (the 1,500 seen from the most networks), and of the rest, those seen longest ago. Before, a full site took no new label, so anyone could stop a site learning for good with a few dozen outlines of made-up labels. Now such a flood is pushed out by the labels real visitors keep seeing, and to keep out new learning it would have to go on.

**What menus show.** When a visitor opens a menu, a tab or an accordion, the widget notes the links and buttons on screen as the control is pressed, looks again several times over about a second and a half until the next press, and sends whatever appeared in any look with the control's label, like `Help` opening `Help center → /help; Keyboard shortcuts; What's new; Contact support`. It is watched from the press and not the click, because menus like Radix's open on the press, and it looks more than once because some people pick from a menu within a few hundred milliseconds. Nothing a field suggests is sent, since suggestions follow what was typed, and nothing that opens from a table's cells. Each control is sent once per page per tab. The server counts each item by distinct visitor in `outline_openings` (`db/migrations/0012`), the same way as page labels, and adds the items enough visitors saw to the page's `opens`, the field the dashboard's reader and the mapper fill in too. Then two things use it: the site map lists `behind "Help": …` for each page, and on the page the visitor is on, a closed control is listed with what it opens, like `e7 button "Help" (collapsed) [header] opens: Help center → /help; Contact support`. A control in the header, navigation or a sidebar gets what it showed on other pages, as long as that was the same everywhere it was seen. One in the main part of the page gets only its own page's, since "More actions" on two pages can open different things.

**On your own machine.** Without a database, what is learned is kept in `data/learned.json`, which `.gitignore` leaves out, so restarting the server doesn't forget the site. A label in an older file that could not be learned today is left out of the prompt. Delete the file to start again.

## What it leaves running

While no guide runs, nothing of the widget's runs on the page: no timer, no animation frame and no observer. What listens is only what something needs while idle: the document's `toggle` events in the capture phase (a page's dialog or popover opening on the top layer, which could cover the launcher), the window's `resize`, and, while the site learns from visits, a passive click listener, passive `pointerdown` and `keydown` listeners that hear a menu, a tab or an accordion being opened, and the address watcher (the browser's Navigation API, with `popstate` and `hashchange`; in a browser without that API, a look at the address every tenth of a second). A press on a control that opens something is the one thing that starts work while idle: five looks at the page over about a second and a half, then nothing. Everything a guide needs is added when it starts and taken away when it ends, a `pagehide` listener for its report among them.

## Where the launcher sits

The launcher is in the window's bottom right corner on every site, and that is not a setting: a visitor always finds it on the right. It only ever moves up that side, never along the bottom and never to the left. A control of the page's that is in the corner for good, like a chat button, a Feedback tab or the footer's last links, sends it up to the nearest free place above (`findHome`). While a guide points at a control that the launcher, or the open chat above it, would cover, they move up to just above the control and its caption, and come back down when the step is over (`keepLauncherOff`). The caption keeps off them first: one that would run under them in their corner, like a long caption under a dialog's last button just left of the chat, moves left as far as it must, and no further than to end at the control's right edge (`captionLeft`; in presentation mode the corner is one more place `presentedCaption` keeps off). Only when it can't clear them that way do they move up for it. When the open chat has no room there, it is tucked away for that step and the launcher alone moves up if it has to. The caption's × still stops the guide, and a click on the launcher brings the chat back for the rest of the step. A site stored with the launcher on the left, from before the choice went, gets it on the right too. `test/widget/placing.test.ts` and `test/browser/chat.test.ts` cover it.

On a page written right to left, with `dir="rtl"` on `<html>`, the launcher and the chat are drawn exactly as on any other: the host is `direction: ltr`, since `all: initial` leaves direction alone, and only words the visitor or the model wrote read right to left, inside their bubbles (`dir="auto"`). `test/browser/rtl.test.ts` covers it.

## Putting the launcher away

A visitor who doesn't want the launcher in the corner can minimize it. A small button with a − shows on the launcher's outer bottom corner while the mouse is over it or it has focus, and turns it into a dot. The dot opens up a little to show the pointer when the mouse is over it, and a click brings the launcher back. The choice is kept in the site's `localStorage` as `haptic.minimized`, so it holds on the next page. Where storage is blocked, the launcher is minimized on that page only. `test/browser/minimize.test.ts` covers it in all three browsers.

## Testing in browsers

`npm run test:browser` runs, in a real browser, how the widget reads pages (`test/browser/snapshot.test.ts` and the files beside it, in Chromium) and the widget itself on small pages against a stand-in server that answers each step from a script (`test/browser/harness.ts`), in Chromium, Firefox and WebKit. `BROWSERS=chromium npm run test:browser` runs one engine. `npm run test:widget` runs the rest of the widget's tests in Chromium: guides, hearing, acting, the gate and the red-team pages (`test/widget/`). The act tests on pages built from the real React, Radix and cmdk need those libraries for the run: `npm install --no-save react@19 react-dom@19 radix-ui@1 cmdk@1`; without them they are skipped. Playwright's browsers are needed once: `npx playwright install chromium firefox webkit`.
