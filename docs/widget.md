# How the widget follows a page

The widget runs on pages it doesn't control. This covers how it keeps up with them: how it reads a page and hears what the visitor does, dialogs, controls something else covers, single-page apps that change the address, Do it with me, what it learns about a site from visits, what it leaves running, and how to test it in real browsers. For the project overview, see the [README](../README.md).

## Reading the page and hearing the visitor

The page is read in one pass (`src/widget/snapshot.ts`): every control with its role, label and state, the headings, and short pieces of visible text, including table rows, menus and lists a page draws itself, controls inside open shadow roots and same-origin frames, controls that show only while the mouse is over them, and sign-in walls. Nothing typed is read: not a field's value, and nothing inside an area a visitor writes in, which is listed as one control and not looked into. What the visitor then does is heard as they do it (`src/widget/observe.ts`): a click, typing in a field, a pick from a list the control opened, a key the sentence asked for, a page load. After the step the model called the last, the widget looks once more at what came of it (a closing question), so a guide does not end on a click nobody checked.

How a guide's ending is reported: the moment the last pointer of a guide that got there shows, and the moment the visitor uses the last control, the outcome is sent at once, with `keepalive`, since the page may be about to go. While a pointer the model called the last is on show and the visitor has not used it, a `pagehide` listener reports it as shown if the tab closes. The guide keeps its id for the look that follows, and nothing is reported twice; the server keeps the first outcome it hears.

## Modal dialogs

A page's modal `<dialog>` makes everything outside it inert, Haptic's own element included. The widget moves its element into the open dialog the moment it opens, shows it again on top, and moves it back out when the dialog closes, so the pointer and the Stop button keep working through nested dialogs too. Escape in Haptic's ask box closes Haptic's panel and not the page's dialog.

## Covered controls

A control on screen that something else covers, like a button under a stack of cards or the page behind a full-screen overlay, is left out of the snapshot, because a visitor can't click it. The browser's own hit test decides, at the control's middle, then around it, then at the middle of each line of a control that wraps (`keepReachable` in `src/widget/snapshot.ts`). A control only scrolled out of its scroll box stays in and is said to be above or below, and so does one under a sticky header or a bar pinned to the window, since pointing scrolls it into view. One under a list, a menu or a box the page opened over it stays too: it is only under it while that is open. A see-through field drawn by a box around it, like a styled tick box, counts as that box, and a layer over the whole window, like a wall of cookie choices, is then all of the page that can be used.

## Route changes

Single-page apps change the address without loading a page, so the widget watches for it itself: through the browser's Navigation API, or by looking at the address every tenth of a second in a browser without it, and never by changing the page's own `history` (`src/widget/navigation.ts`). If the address changes while the model is answering, the answer is about a page the visitor has left, like the page they were on when they clicked something that took a moment to load. The widget hangs up at once and asks again from the new page, and the server stops the model call and counts the dropped step on the guide (`cancelled_steps`). An app that changes the address first and draws the page a moment later is waited for: a new address over the same controls as before has not been drawn yet.

## Do it with me

Off unless the company turns it on for its site (`npm run tag -- acting <site id> on`, then publish; `acting.paths` limits it to parts of the product, and `commitWords`, `maxActions` and `confirmFirst` tune it). A page can turn it off for itself with `data-acting="off"` on the script tag, never on. The ask box then has a Do it button beside Send. Haptic clicks, types and chooses on the page while the visitor watches (`src/widget/act.ts`), and every action first passes the gate (`src/widget/gate.ts`): it never presses anything that saves, sends, pays or deletes, never types passwords or payment details, and types only what the visitor wrote in their question. A link is judged as a button is, by its words and by where it leads ("/expenses/7/approve" approves). Only a link that visits another page of the site and whose words and address commit nothing is pressed for what it is, and every link press is watched: a page that answers it by sending something to its server stops acting at once. The server checks every reply with the same rules (`src/shared/act-rules.ts`) before the widget sees it. At the last control, the one that commits, it points and hands over: the visitor makes that click. The visitor's own click or key pauses it, Escape stops it, Back ends it, and the panel lists what it did. To check that its own typing took, it reads that field's value inside the browser, and never sends it. Dates are not picked in this version. Answers is never used for a step Haptic was asked to do. The code that acts, with the gate and the word tables, is a second file, `widget-act.js`, served beside `widget.js` by the same server (`src/widget/acting-code.ts`). Only a site with acting on loads it, as the widget starts, so most pages never fetch it, and a policy that allows Haptic's script allows it too (a policy that names the one file `widget.js`, rather than Haptic's address, would need the second file named as well). If it does not come, the site is guided by pointer, and Do it is not shown.

## Learning the site from visits

The crawl builds the first map of a site, but it can't sign in, and it can't open what only a click reveals. So the widget also sends an outline of each page it loads on, once per page per tab, when the page has settled and the browser is idle (`src/widget/learn.ts`): the title, headings, and the labels of its links and buttons, with an icon-only button named by its icon, like `icon:share-2`. When a click is followed by a new page within eight seconds, it sends the clicked label as a link on the page the click came from, like "View, in a dialog → /set/:id", which is how Haptic learns a page that only a dialog leads to. Labels only: never what is typed into a field, never what is in a table's cells, and a label holding an email address or a long number is dropped whole.

Each label is counted by distinct visitor (`src/server/learned.ts`). The widget keeps a random id in the site's `localStorage`, and the server keeps only a hash of it made with the site's id, up to ten per label, in `outline_labels`. A browser that keeps no storage has no id, and what it sends is not used: a hash of a network address could be turned back into the address. A label reaches the prompt only once enough different visitors have seen it: 3 online, 1 on your own machine, or `HAPTIC_LABEL_THRESHOLD`. That keeps one person's own data, like the name of their project, out of everyone's prompt. What is learned is merged with the crawl's pages when a site is read from the database, so a step never waits on it. The crawl's pages come first, pages only traffic knows follow, navigation that is on most pages is listed once, and each page lists at most 24 buttons. Learned labels are listed in a fixed order, so a count going up does not change the prompt the model provider keeps cached. A site whose context has `"learn": false` sends no outlines.

**What menus show.** When a visitor opens a menu, a tab or an accordion, the widget notes the links and buttons on screen as the control is pressed, looks again several times over about a second and a half until the next press, and sends whatever appeared in any look with the control's label, like `Help` opening `Help center → /help; Keyboard shortcuts; What's new; Contact support`. It is watched from the press and not the click, because menus like Radix's open on the press, and it looks more than once because some people pick from a menu within a few hundred milliseconds. Nothing a field suggests is sent, since suggestions follow what was typed, and nothing that opens from a table's cells. Each control is sent once per page per tab. The server counts each item by distinct visitor in `outline_openings` (`db/migrations/0012`), the same way as page labels, and adds the items enough visitors saw to the page's `opens`, the field the dashboard's reader and the mapper fill in too. Then two things use it: the site map lists `behind "Help": …` for each page, and on the page the visitor is on, a closed control is listed with what it opens, like `e7 button "Help" (collapsed) [header] opens: Help center → /help; Contact support`. A control in the header, navigation or a sidebar gets what it showed on other pages, as long as that was the same everywhere it was seen. One in the main part of the page gets only its own page's, since "More actions" on two pages can open different things.

**On your own machine.** Without a database, what is learned is kept in `data/learned.json`, which `.gitignore` leaves out, so restarting the server doesn't forget the site. Delete the file to start again.

## What it leaves running

While no guide runs, nothing of the widget's runs on the page: no timer, no animation frame and no observer. What listens is only what something needs while idle: the document's `toggle` events in the capture phase (a page's dialog or popover opening on the top layer, which could cover the launcher), the window's `resize`, and, while the site learns from visits, a passive click listener, passive `pointerdown` and `keydown` listeners that hear a menu, a tab or an accordion being opened, and the address watcher (the browser's Navigation API, with `popstate` and `hashchange`; in a browser without that API, a look at the address every tenth of a second). A press on a control that opens something is the one thing that starts work while idle: five looks at the page over about a second and a half, then nothing. Everything a guide needs is added when it starts and taken away when it ends, a `pagehide` listener for its report among them.

## Putting the launcher away

A visitor who doesn't want the launcher in the corner can minimize it. A small button with an × shows on the launcher's outer bottom corner while the mouse is over it or it has focus, and turns it into a dot. The dot opens up a little to show the pointer when the mouse is over it, and a click brings the launcher back. The choice is kept in the site's `localStorage` as `haptic.minimized`, so it holds on the next page. Where storage is blocked, the launcher is minimized on that page only. `test/browser/minimize.test.ts` covers it in all three browsers.

## Testing in browsers

`npm run test:browser` runs, in a real browser, how the widget reads pages (`test/browser/snapshot.test.ts` and the files beside it, in Chromium) and the widget itself on small pages against a stand-in server that answers each step from a script (`test/browser/harness.ts`), in Chromium, Firefox and WebKit. `BROWSERS=chromium npm run test:browser` runs one engine. `npm run test:widget` runs the rest of the widget's tests in Chromium: guides, hearing, acting, the gate and the red-team pages (`test/widget/`). The act tests on pages built from the real React, Radix and cmdk need those libraries for the run: `npm install --no-save react@19 react-dom@19 radix-ui@1 cmdk@1`; without them they are skipped. Playwright's browsers are needed once: `npx playwright install chromium firefox webkit`.
