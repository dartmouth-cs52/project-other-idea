## Part 1. What does arXiv:2510.04607 actually say? (verified reading; corrections to the second-hand summary)

### Takeaway
The second-hand summary is accurate on every number it gives, including the crucial ablation: giving the baseline agent the navigation forest as prompt knowledge without the declarative `visit` interface left GPT-5 at 42.0% SR / 8.41 steps versus 44.4% / 8.16 for the plain baseline, and the authors conclude "the declarative interface, not the static knowledge, is the primary source of DMI's effectiveness." Three things the summary omits matter for the product: (1) the same ablation on the weaker GPT-5-mini did show a modest gain from knowledge alone (17.3% to 23.5% SR, 7.14 to 6.32 steps); (2) the "single LLM call" claim means 4 LLM calls per task of which 3 are fixed framework overhead, and a successful DMI task still took 239 s on average; (3) the authors explicitly name web browsers / the DOM as the case their navigation abstraction does not yet handle.

### Cited Findings

**Identity, versions, venue, artifacts**
- Title "From Imperative to Declarative: Towards LLM-friendly OS Interfaces for Boosted Computer-Use Agents"; authors Yuan Wang, Mingyu Li, Haibo Chen; v1 submitted 6 Oct 2025, v2 25 Mar 2026; primary class cs.OS; related DOI 10.1145/3767295.3803576 — [arXiv abs](https://arxiv.org/abs/2510.04607)

The v2 HTML header reads "21st European Conference on Computer Systems (EUROSYS '26), April 27–30, 2026, Edinburgh, Scotland Uk", and the acknowledgments thank "the anonymous reviewers of EuroSys 2026" and "our shepherd Jayson Boubin" — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2). Crossref lists the DOI in "Proceedings of the 21st European Conference on Computer Systems", 2026, pages 296–310 — [Crossref record](https://api.crossref.org/works/10.1145/3767295.3803576)
- v1 used a different name for the same system: "Goal-Oriented Interface (GOI)"; v2 renamed it "Declarative Model Interface (DMI)". Headline numbers are identical in v1 and v2 — [arXiv HTML v1](https://arxiv.org/html/2510.04607v1); [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- Code: the paper says "DMI comprises over 18K lines of Python code and leverages the pywinauto library" with footnote "DMI will be released at https://github.com/dmi-interface/DMI" (§4) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- That repository exists (checked 12 Nov 2026): public, MIT licence, 2 commits, 5 stars, built on microsoft/UFO. Its README says the repo "focuses on open-sourcing and reproducing the DMI execution layer" and ships "prebuilt core English topologies" for Word, Excel and PowerPoint in OSWorld-Windows. The README does not mention the offline modeler / GUI ripper — [GitHub repo](https://github.com/dmi-interface/DMI)

**The three primitives and the `visit` interface (§3.1, §3.4, §3.5, Table 2)**
- Access: "Given a control identifier, DMI deterministically navigates from any current state to that control and performs a primitive interaction (e.g., click)." State: "Given a desired control end state (e.g., scrollbar position; selection state for a control or for text), DMI transitions the control from any current state to the target state". Observation: "Given an information request (e.g., a control's text content), DMI returns structured data rather than relying on pixel-level recognition" (§3.1) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- "`visit` accepts an array of structured commands and executes them sequentially in a single call." Four command types: control access `{"id": "<target_id>"}` (plus `"entry_ref_id"` for targets in a shared subtree), access-and-input-text `{"id":..., "text":...}`, auxiliary `{"shortcut_key":...}`, and `{"further_query": [...]}` (§3.4) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- The executor, not the LLM, does the navigation: "The executor traverses this path from the current UI state. On each iteration, it fetches the topmost valid window and all descendant controls, and matches the parsed path from the end backward against the visible hierarchy. If no control from the remaining path exists in the current window, it closes that window." (§4.3) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- LLMs disobey the "targets only" instruction, so non-leaf nodes are filtered: "We filter out non-leaf nodes, allowing the executor to retain only commands targeting functional nodes and handle navigation independently." (§3.4) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- Forced observation points: "`visit` excludes complex interactions ... DMI requires the LLM to stop emitting further visit commands. This forces the LLM to observe ... before re-planning based on the actual UI state. DMI disallows mixing visit interface with other interfaces in the same turn" (§3.4). State/observation interfaces (Table 2: `set_scrollbar_pos`, `select_lines`, `select_paragraphs`, `select_controls`, `get_texts`) may not use static IDs from the topology; they "can only operate on controls specified by their label from the current screen's accessibility tree" (§3.5) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- Robustness mechanisms in the executor: "a fuzzy control matcher that combines control type, ancestor hierarchy, and name similarity when exact matching fails due to name variations or UIA's lack of guaranteed unique identifiers"; "structured error feedback ... e.g., when a target control is located but disabled"; "a failure retry mechanism for GUI controls that may load slowly" (§3.4) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)

**Offline modeling (§3.2, §3.3, §4.1, §4.2)**
- "The result is a UI Navigation Graph (UNG): nodes are UI controls and directed edges denote 'click' interaction." Keyboard shortcuts are not modeled as edges (§3.2) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- GUI ripping: "The UNG is built via differential capture. Exploration proceeds with depth-first search (DFS). First, obtain the accessibility tree of the target application, from which a list of UI controls is captured. Then activate a candidate control (i.e., click) from the list and capture again. Newly revealed controls define navigation edges. New top-level or modal windows are detected via process_id and window listeners. The exploration is fully automated." (§4.1) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- Node identifiers: "Since UIA lacks guaranteed globally unique identifiers, we adopt an XPath-like control identifier: `primary_id|control_type|ancestor_path`" where primary_id is the UIA automation_id, falling back to the control name or "[Unnamed]". "We avoid index-based addressing since dynamic menus can shift indices unpredictably." (§4.1) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- Graph to DAG to forest: "First, we decycle the graph to a DAG ... identifying and removing back-edges that form the cycles." Then a "cost-based selective externalization algorithm" handles merge nodes: when cloning cost "exceeds a configurable threshold, the node and descendants are externalized as a shared subtree, with incoming edges redirected to new reference nodes"; otherwise the substructure is cloned. "The resulting structure is a forest, comprising a main tree and a set of shared subtrees." Naive full cloning "exceeds the available context window of the LLM (400K tokens, GPT-5) in our experiment." (§3.2) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- Why paths cannot simply be deduplicated: "in Word's color picker, a color cell is reachable via 'Font Color,' 'Outline Color,' or 'Underline Color'; the chosen path determines which property is modified." (§2.4) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- Core topology and `further_query`: "DMI by default provides a limited-depth core (e.g., six levels) instead of the complete forest, excluding large enumerations (font lists) and manually identified nodes. While pruning rules are currently manual, future versions could leverage LLM assistance for automation." `further_query` supports "(a) targeted branch queries expanding sub-structures beneath specified nodes, and (b) global queries retrieving the complete forest"; it "is exclusive and cannot be mixed with other commands in the same call" (§3.3, §3.4) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- Serialization: "`name(type)(description)_id[children]`"; "The name, type, and description are drawn solely from UIA properties provided by the application. The id is a unique, consecutive integer used for concise references" (§4.2) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- Manual parts of modeling. Blocklist: controls that "trigger external transitions (e.g., an 'Account' button opening a Web browser)" or "bring the application into states that cannot be exited using standard commands like Esc or Close" are handled with "a manual blocklist"; "Maintaining the blocklist constitutes most of the manual effort". Context: "Some controls are implicitly state-dependent ... (e.g., PowerPoint's 'Picture Format' tab appears only when an image is selected) ... We manually instantiate representative objects ... automating it remains challenging. Omitting it would compromise the completeness of the UNG." (§4.1) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)

**Modeling cost and graph size (§5.2, §5.4) — summary confirmed**
- "In the raw modeled graphs, Excel/PowerPoint/Word each exceeds 4K controls. To control context cost, we extract a core topology from the forest: Excel ≈ 2K, Word ≈ 1K, and PowerPoint ≈ 1K controls. Word and Excel take a forest; PowerPoint's core topology is a single tree." (§5.2) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- "Automated modeling per application takes < 3 hours. Some manual setup is required ... Average manual effort is around 1.5 person-days per application. The resulting model is version-specific but reusable across machines for the same application build." (§5.2) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- "each control contributes ~15 tokens on average (measured under the o200k_base encoding). The core topologies add approximately 30K (Excel), 15K (Word), and 15K (PowerPoint) tokens." "Over 80% of this overhead comes from the navigation forest". "DMI reduces interaction rounds substantially, resulting in total token usage per task being lower than the baseline in the core scenario." (§5.4) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- Internal inconsistency on app size: §2.4 says ">5,000 in Microsoft Office" and §5.1 says the apps "expose over 5,000 controls each", while §5.2 says the raw modeled graphs "each exceeds 4K controls" — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)

**Setup (§5.1)**
- Benchmark: "the OSWorld-W (Windows) portion comprising 27 single-app scenarios for PowerPoint, Excel, and Word"; multi-app tasks excluded. "Each task is capped at 30 steps ... and is run three times, then averaged." Models: GPT-5 (medium and minimal reasoning) and GPT-5-mini; "No fine-tuning is applied." — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- Baseline: Microsoft UFO-2 in the configuration "UFO2-base + action sequence (denoted UFO2-as)". UFO-2's Office COM APIs "are not general and are therefore excluded." The baseline can already emit multiple actions per turn "provided all referenced controls are currently visible in the app UI." With DMI enabled, "the LLM may fall back to the baseline's imperative GUI primitives" — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)

- What "single LLM call" means: "In the core setting, with DMI, over 61% of successful trials are completed in 4 steps. ... UFO-2's workflow incurs a fixed 3-step overhead. **The knowledge-only ablation (§5.5 "Ablation Study", Table 3 rows 2 and 7, Figure 5) — the most important passage, quoted in full**
- "To determine whether DMI's performance gains stem from its declarative interface or simply from providing a static knowledge base, we conducted an ablation study on both large and small models, as shown in Table 3 and Figure 5. For the baseline UFO2-as, we provided the DMI navigation forest in the prompt while disabling the declarative interface. This configuration yields no significant change in performance (SR 42% vs. 44% baseline; Steps 8.41 vs. 8.16, Normalized Steps 8.58 vs. 7.94), indicating that the declarative interface, not the static knowledge, is the primary source of DMI's effectiveness. In contrast, the less capable GPT-5-mini model shows a modest improvement when given the forest alone (SR 23.5% vs. 17.3% baseline; Steps 6.32 vs. 7.14; Normalized Steps 6.26 vs. 7.02). This suggests that supplementary topology knowledge can be helpful for models with less general-purpose knowledge. Crucially, however, the full DMI setting produced much larger gains (SR 43.2%; Steps 4.43; Normalized Steps 4.52), confirming that the interface design is the dominant performance driver. The average time is slightly lower as the baseline succeeds on short/easy cases." — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- Precisely what the ablation did: same agent framework (UFO2-as, imperative click/type primitives over currently visible controls), same model, with the same serialized navigation forest that DMI uses added to the prompt, and the `visit`/state/observation interfaces disabled. It was run for GPT-5 medium and GPT-5-mini medium only (there is no ablation row for GPT-5 minimal) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- "Normalized steps" are computed "on the intersection of tasks successfully solved by all compared methods": 7.94 (GUI-only), 8.58 (ablation), 4.60 (GUI+DMI) for GPT-5 medium (§5.3) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- Failure behaviour in the ablation resembled the baseline: "We observed similar errors in the ablation experiment, reinforcing that coupling policy with mechanism leads to avoidable mistakes." (§5.6) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)

**Failure analysis (§5.6, Figure 6)**
- GUI+DMI failures: "ambiguous task descriptions (42.9%); misinterpretation of control semantics (28.6% ...); weak visual-semantic understanding (14.3%); misunderstanding of subtle task semantics (9.5%); and topology/modeling inaccuracies (4.8%)". Evaluation takeaway: "most failures are policy-level (81%, semantic planning); only 19% are mechanism-level" — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- GUI-only baseline failures: "control localization and navigation errors (14/45), and composite-interaction errors (7/45) ... additional task-semantic errors and misperception of control functionality (6/45). A further 18 failures overlap with the policy-centric categories above." — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)

**Limitations and lessons (§5.7, §6)**
- Web / DOM: "Applications might be driven by a dynamic UI that resists comprehensive pre-modeling. A canonical example is the Web browser. The main challenge of adapting DMI to Web browsers is the high volatility of Web controls—DOM structures and element attributes frequently change due to dynamic content rendering and continuous updates. This complicates navigation abstraction (access declaration) compared to relatively stable desktop applications. Handling dynamic controls is a challenging and promising direction for future work. Nevertheless, DMI's state and observation declarations target UI controls interaction (e.g., set a scrollbar position, checkbox state, text in edit_box), and thus can smoothly adapt to browsers." (§6 "Handling dynamic controls") — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- Conditional controls and identifier stability: "Our prototype infers edges by comparing accessible trees before and after a click action, but cannot capture all dependencies. For example, in Word's 'Find and Replace' dialog, entering special text (e.g., +1, +2, +3) into the 'Rich Edit' control dynamically renames the 'Next' button to 'Go To'. Depth-first search exploration may miss such conditional changes, and without stable application identifiers, name changes break element matching. When topology is incomplete, LLMs can fall back to GUI-based imperative primitives, but may still fail due to poor visual localization of LLMs." (§6 "(In)accurate navigation topology") — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- Identifier lesson: "A critical lesson is the need for applications to expose globally unique identifiers for controls. Although UIA recommends AutomationId, its global uniqueness is not enforced. As a result, current control identification methods like XPath are not reliable." Description lesson: "Comprehensive and explicit descriptions in accessibility metadata are crucial ... Future work can augment the textual navigation topology with descriptions synthesized from documentation or curated by LLMs." (§5.7) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- Manual effort and version specificity: "Extending DMI to new applications necessitates constructing an application-specific UNG ... this involves manual configuration"; model is "version-specific" (§6, §5.2) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- Coverage limits: DMI "cannot simplify all complex interactions" (free drawing, position-precise manipulation); "DMI is the fast path used by default; GUI is the slow-path fallback"; legacy apps and games without UIA trees are out of scope (§6) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)
- Planning risk the authors name themselves: "Since the navigation topology is deterministic, the LLM can plan multiple commands in a single call ... However, this makes subsequent commands contingent on earlier correctness: unexpected intermediate outcomes can invalidate subsequent steps and cascade into task errors." (§2.4, Challenge #3) — [arXiv HTML v2](https://arxiv.org/html/2510.04607v2)

### Inferences
- Sample size. 27 tasks × 3 runs = 81 trials per configuration. The reported percentages correspond to 36/81 (44.4%), 34/81 (42.0%), 60/81 (74.1%) for GPT-5 and 14/81 (17.3%), 19/81 (23.5%), 35/81 (43.2%) for GPT-5-mini. The knowledge-only ablation therefore differs from the baseline by 2 trials (GPT-5) and 5 trials (GPT-5-mini). The paper reports no confidence intervals or significance tests; "no significant change" and "modest improvement" are the authors' descriptive words, not statistical results.
- Per-call latency implied by Table 3 (my division, successful runs only): about 48 s per LLM call for GUI-only (392/8.16) and about 52 s for GUI+DMI (239/4.61) with GPT-5 medium. DMI's speed-up comes entirely from fewer calls, not faster calls.
- The mechanism that produced the gain is that a deterministic executor performs the multi-hop navigation itself, so those hops cost zero LLM calls. In a guide-the-human product the executor is a person; DMI's result does not transfer as "the map makes each step faster". The closest transferable analogue (my inference, not a finding of the paper) is: one LLM call selects the target control, then a precomputed path supplies each subsequent pointer position without an LLM call, with a cheap local check that the live DOM matches the expected node.
- The repo release appears to cover the execution layer and the three Office topologies, not the ripper; anyone wanting to reproduce the offline modeling would have to re-implement §4.1. This is inferred from the README's wording, which does not explicitly say the modeler is withheld.
- The baseline already bundled several visible-control actions per turn, so the measured step reduction is specifically the benefit of planning over controls that are not yet visible.

### Gaps
- No experiment in the paper involves a web application, a logged-in app, or a human in the loop.
- The paper does not report how often the fuzzy matcher, retries or GUI fallback fired, nor graph staleness across Office builds.
- I could not open the ACM DL page (HTTP 403) to check for artifact badges; venue and pages come from the arXiv HTML header and Crossref.

## Part 2. What does the adjacent literature report? (per-paper notes: acquisition, stored artifact, inference-time use, gains, limits)

### Takeaway
Across web, mobile and desktop, offline site/app knowledge reliably raises success rates, but large reductions in LLM calls and wall-clock time appear only when the knowledge is paired with an executable mechanism that skips LLM calls (teleport/pathfinding, compiled skills or tools, cached sub-task replay, one-shot program synthesis). Knowledge that is only read by the model (text workflows, cognitive maps, retrieved experiences) changes step counts by roughly 0–25% in the papers that report it; the largest reductions (37–45% fewer steps, or 4–6× fewer LLM calls) all come from executable mechanisms, although not every executable mechanism achieves them (ASI −11%, WebNavigator −11 to −12%).

### Cited Findings

#### 2.1 Explicit navigation graphs / state machines for websites (closest web analogues of DMI)
- **WebNavigator** (Zhang et al., arXiv:2603.20366, v1 20 Mar 2026; arXiv comment "Accepted at NeurIPS 2026"). Acquisition: offline "Heuristic Auto-Exploration Engine", an adaptive BFS that clicks dynamic elements and uses DOM differencing against the parent state; "zero-token cost, requiring no LLM involvement and only a homepage URL as input"; "a configurable block list to exclude hazardous operations and external links". Stored: an "Interaction Graph" whose nodes are page observations (screenshot + DOM + accessibility tree) "uniquely indexed by hashing its structural components Hash(o_str, url), where each web element is identified via deterministic XPath rather than dynamically assigned BIDs", embedded in a vector index. Use: one high-level action `navigate(domain, query)` = Retrieve top-k screenshots, a multimodal selector LLM picks one (or None), then "Teleport" executes the shortest path "with zero-token cost". The authors state "Directly providing the complete Interaction Graph G to LLMs is impractical due to context window constraints." — [arXiv 2603.20366](https://arxiv.org/abs/2603.20366)
- WebNavigator results: WA 49.9% (GPT-4o), 57.1% (Claude Sonnet 4), 63.3% (Gemini 2.5 Pro); WA multi-site 72.9% (Gemini 2.5 Pro); OM2W 52.7% (Gemini 2.5 Pro), 41.3% (GPT-4o) (§4, Table 1). Steps (Table 9): 8.93 vs 10.14 for AgentOccam with Claude Sonnet 4 and 8.98 vs 10.10 with Gemini 2.5 Pro; multi-site 11.75 vs 14.56 (−19.3%) and 10.75 vs 14.96 (−28.1%). Wall-clock per task was essentially unchanged: 635.1 s vs 643.3 s (Claude Sonnet 4) and 753.5 s vs 773.6 s (Gemini 2.5 Pro). Tokens per task went up: 123,684 vs 67,351 (Table 17). The navigate workflow itself costs 15.6 s per task: retrieve 2.2 s, selector LLM 11.1 s, teleport 2.3 s (Table 16) — [arXiv 2603.20366](https://arxiv.org/abs/2603.20366)
- WebNavigator construction cost (Tables 5, 15): Map depth 1, 16 nodes, 2.1 min; CMS depth 2, 122 nodes, 23.1 min; Shopping depth 2, 570 nodes, 122.1 min; GitLab depth 2, 838 nodes / 1,659 edges, 316.8 min ("approximately $0.90" of CPU on AWS c7i.xlarge); Reddit depth 3, 225 nodes, 31.1 min. Embedding/indexing adds 0.31–21.75 min and at most $1.26 per domain. Graphs are "highly sparse and tree-like, with branching factors ranging from 1.10 to 1.98". For the 136 live OM2W sites only depth-1 exploration was used — [arXiv 2603.20366](https://arxiv.org/abs/2603.20366)
- WebNavigator on completeness: SR on WA-Reddit rises with exploration depth, 63.2% (depth 1), 70.8% (2), 73.6% (3), 75.5% (4) (§5.1, Fig. 3). Click-only exploration found 16/16 human-annotated "functional entry points" on Reddit at depth 3, the same as an LLM-assisted explorer that also types into inputs (Appendix I, Table 14). Retrieval alone is not enough: top-1 retrieval accuracy 22.97–63.83%, selector accuracy 75.82–96.72% (Table 3). Selector returns None on 3.6–9.1% of tasks and the agent falls back to ReAct-style actions, succeeding on 43.6–62.2% of those (Table 10). Replacing the graph with an empty graph regressed 95 of 514 previously solved tasks (Appendix K) — [arXiv 2603.20366](https://arxiv.org/abs/2603.20366)
- WebNavigator remaining failures: "retrieval failure accounts for only 12.4% of all failures ... The dominant failure mode is execution failure at 58.7%, where the agent reaches the correct page but fails due to LLM limitations in local reasoning" (§5.2). Stated limits: upfront graph construction per site; canvas-rendered sites unsupported; manual choice of depth; harness corner cases ("observations may be captured before a page has fully loaded", element IDs "may become invalid by the time an action is executed"). Maintenance (Appendix D) is a periodic re-verification crawl of all nodes and edges plus incremental exploration from newly added elements; no measurement of drift is reported — [arXiv 2603.20366](https://arxiv.org/abs/2603.20366)
- **ActionEngine** (Zhong et al., author list includes Microsoft researchers, arXiv:2602.20502, v1 24 Feb 2026, v2 28 Sep 2026; no venue listed on arXiv). Acquisition: an LLM-driven "Crawling Agent explores the application offline" with black-box access. Stored: an updatable "state-machine memory" (SMG) serialized as YAML "containing the states, operations, actions, locators, descriptions, inputs, outputs, and transitions"; each operation is validated against the live site. Use: the Execution Agent "synthesize[s] a complete executable program in a single planning step, which is then executed deterministically without further planning calls"; a "Patcher" re-grounds failed actions and "commits the repair back to the SMG" — [arXiv 2602.20502](https://arxiv.org/abs/2602.20502)
- ActionEngine results (Table 1, 655 WA tasks in four domains, all systems on Claude Opus 4.6): SR 91.2% vs 82.7% for Claude Code + Playwright MCP vs 56.8% for AgentOccam; average latency 27 s vs 87 s vs 787 s; "from 7–16 calls per task for reactive baselines to 1.5–3.5 for ActionEngine"; API cost $0.05 per task vs $0.40 (Claude Code) and $0.34 (AgentOccam). Crawling "takes 36–260 minutes and costs $11.6–$37.2" per application and breaks even "after 39–101 tasks" (§5.2, §5.3) — [arXiv 2602.20502](https://arxiv.org/abs/2602.20502)
- ActionEngine caveats stated in the paper: the reported 91.2% uses an SMG refined in a "warm-up" phase that runs "one task for each WebArena task template" with the Patcher on; with the crawler-only SMG the SR is 73.1% ("Refinement further improves success across all four domains, with an average improvement of 18.1 percentage points"). Refinement repairs were "(1) Selector and locator repairs: the crawler sometimes produces CSS selectors that do not trigger the intended JavaScript event handlers ... the Patcher replaces these with Playwright role-based locators", "(2) Timing fixes", "(3) Description enrichment". The Patcher was disabled during evaluation. Failed tasks were manually re-reviewed for all methods and format-only mismatches counted as successes. Remaining failures: "ambiguous task intent (~23 cases) or search-dependent tasks (~22 cases). The latter expose a key limitation of plan-then-execute agents: the Planner must choose search terms before observing the results" — [arXiv 2602.20502](https://arxiv.org/abs/2602.20502)
- **WebChallenger** (Hwang, Zhang, Padwal, arXiv:2606.10423, 9 Jun 2026). Acquisition: "Exploration is fully deterministic: it requires no LLM guidance, task demonstrations, or external resources"; depth-first clicking with element de-duplication, state restored "by reloading the pre-click URL"; limits of 75 clickable elements per page, 500 pages per site, depth 2 and a 12-hour timeout per site (depth 1 and 1 hour for the 136 OM2W sites). Stored: per-site JSON "WebsiteMem" of PageMems (DOM-derived section hierarchy with summaries), page templates and element behaviours such as dropdown contents. Use: "only a handful of extra tokens are added per prompt"; the agent picks "bookmarks" as navigation shortcuts — [arXiv 2606.10423](https://arxiv.org/abs/2606.10423)
- WebChallenger results with open-weight models (GLM-4-32B): 56.3% WA, 48.7% VWA, 51.0% OM2W, 70.9% WorkArena. Ablation on WA-lite (Tables 2, 3): full 58.8%; without memory 51.2% (−7.6 points); without compound actions 49.1% (−9.7); without the observation pipeline 41.2% (−17.6). Average steps: 7.20 full, 7.34 without memory, 9.85 without compound actions, 11.26 without the observation pipeline. "On Reddit, removing memory has no effect (71.4 in both conditions)". Stated limit: "a larger number of sequential LLM calls, which increases wall-clock time per task" — [arXiv 2606.10423](https://arxiv.org/abs/2606.10423)
- **R2D2** (Huang et al., arXiv:2501.12485, ACL 2025). Stores previously visited observations as a directed graph ("replay buffer") and uses A* search over it on later attempts, plus a reflective memory of corrected trajectories. Claims "navigation-related failures ... account for approximately 60% of their operational errors", "approximately a 50% reduction in navigation errors and a threefold increase in overall task completion rates" on WebArena. The gain accrues over repeated episodes on the same tasks (Fig. 4) — [arXiv 2501.12485](https://arxiv.org/abs/2501.12485)
- **WebATLAS** (Cheng et al., arXiv:2510.22732, NeurIPS 2025 Workshop on Language Agents and World Models). Acquisition: "lightweight explorer subagents" with coverage incentives and no task reward, then LLM "trajectory-mining". Stored: a "Cognitive Map" of state transitions plus "Semantic Memory" of site constraints. Ablation on WA-Lite (Table 2, average incl. multi-site): AgentOccam base 47.9%; base + raw-HTML cognitive map 44.8%; base + LLM-summarized cognitive map 57.4%; base + hierarchical planner 50.9%; full system with look-ahead 63.0%. The authors' words: "augmenting the agent with the direct HTML cognitive map (Base + CM-Raw) initially reduced performance but led to a dramatic improvement in performance after we enabled agentic summarization" — [arXiv 2510.22732](https://arxiv.org/abs/2510.22732)
- **Go-Browse** (Gandhi & Neubig, arXiv:2506.03533). Frames exploration as graph search over URLs with a frontier, proposing and checking feasible tasks per page; produced "10K successful task-solving trajectories and 40K interaction steps across 100 URLs" on WebArena; used to fine-tune a 7B model to 21.7% WA (not as inference-time memory) — [arXiv 2506.03533](https://arxiv.org/abs/2506.03533)

#### 2.2 Workflow / skill / tool memory for web agents
- **Agent Workflow Memory (AWM)** (Wang, Mao, Fried, Neubig, arXiv:2409.07429). Acquisition: workflows induced by an LLM from past trajectories, offline from annotated examples or online from the agent's own test-time runs. Stored: text workflows (description + abstracted steps with variables). Use: added to the prompt. Table 1 (WebArena, GPT-4): AWM 35.5% SR vs 23.5% BrowserGym baseline ("51.1% relative"); 5.9 steps vs 7.9 for the BrowserGym ax-tree baseline ("about 2.0 fewer steps per example"). Mind2Web: 24.6% relative gain. Limits stated: "AWM online induces workflows from model-predicted trajectories that are not always correct, thus can lead to incorrect workflows"; when workflows were exposed as callable actions, agents "call workflow actions in merely 18.5% of the tasks", and a pre-determined action sequence fails on dynamic intermediate states (the book-flight example where pop-up airport choices are not observed) — [arXiv 2409.07429](https://arxiv.org/abs/2409.07429)
- **Agent Skill Induction (ASI)** (Wang, Gandhi, Neubig, Fried, arXiv:2504.06821). Skills are executable programs induced online and verified by execution before entering the action space. Table 1 (WebArena, Claude 3.5 Sonnet): vanilla 32.7% SR / 5.6 steps; AWM 36.3% / 5.9; ASI 40.4% / 5.0. Abstract: "+23.5%" and "+11.3%" SR over the static agent and the text-skill agent, "reducing 10.7–15.3% of the steps". Only "15.6% of the turns" produced programs that pass verification. Verified programs kept only as prompt memory were 3.7 points worse than putting them in the action space ("we observe many cases where the agent tries to call the skill programs but unsuccessfully, since they are not supported in the action space"). On site transfer, "some skills may be incompatible with alternative website designs" and are updated online — [arXiv 2504.06821](https://arxiv.org/abs/2504.06821)
- **SkillWeaver** (Zheng et al., arXiv:2504.07079). Acquisition: autonomous exploration, "160 iterations with GPT-4o" per website, proposing skills, practising them, and distilling them into Python/Playwright APIs with unit tests. Gains: "relative success rate improvements of 31.8% and 39.8%" on WebArena and real websites; APIs from a strong agent raise a weaker agent "up to 54.3%". Limits: "LLMs like GPT-4o are still not robust enough at API calling" (wrong API or wrong parameters); an appendix case shows the agent "fails to call this API during the task execution"; skills that need real data could not be verified ("does not have access to a list of emails that can appropriately be used as test cases"); the exploration prompt says "Do not interact with login/logout/user accounts on any site." The abstract and body do not report a step-count comparison that I could find — [arXiv 2504.07079](https://arxiv.org/abs/2504.07079)
- **WALT** (Prabhu et al., arXiv:2510.01524). Acquisition: offline "demonstrate-generate-validate loop" per site; a browser agent demonstrates site functions (search, filter, sort, post, comment), a tool-construction agent turns traces into validated action scripts with input schemas, prefers "stable DOM selectors and store[s] element hashes", and promotes UI chains to URL operations where the site exposes them. Results: 52.9% VWA, 50.1% WA; "improving performance by as much as 30.7% (relative) and efficiency by 1.4x". Table 2 (VWA-Classifieds): GPT-5-mini 8.9 steps / 57.5% without tools vs 6.5 steps / 61.5% with discovered tools; tools built from human demonstrations gave 7.4 steps / 66.0% (the highest SR); full system 7.0 steps / 64.1%. Limits: "Offline tool discovery incurs an exploration and validation cost per-website ... Highly dynamic interfaces, A/B experiments, CAPTCHAs, and heavy anti-automation can reduce determinism or block URL promotion. Schemas may still miss rare parameter values; selector stabilization can drift after major redesigns ... broader external validity (e.g., enterprise apps) remains to be tested." — [arXiv 2510.01524](https://arxiv.org/abs/2510.01524)
- **PolySkill** (Yu, Li, Shi, Qi, arXiv:2510.15863). Separates a skill's abstract interface from site-specific implementations; abstract reports skill reuse improved "1.7x on seen websites", SR up "to 9.4% on Mind2Web and 13.9% on unseen websites, while reducing steps by over 20%" — [arXiv 2510.15863](https://arxiv.org/abs/2510.15863)
- **Synapse** (Zheng et al., arXiv:2306.07863, ICLR 2024). Stores full human-demonstration trajectories with abstracted states and retrieves them as exemplars; "99.2% average success rate" on MiniWoB++ and "56% relative improvement in average step success rate" on Mind2Web — [arXiv 2306.07863](https://arxiv.org/abs/2306.07863)
- **ICAL** (Sarch et al., arXiv:2406.14596; publication venue not verified here). Turns sub-optimal demonstrations into annotated examples with human feedback; "In VisualWebArena, retrieval-augmented GPT-4V with ICAL improves task success 1.6x" — [arXiv 2406.14596](https://arxiv.org/abs/2406.14596)
- **AutoGuide** (Fu et al., arXiv:2403.08978). Extracts context-conditional natural-language guidelines from offline experiences and retrieves the ones matching the current state; the abstract claims it "significantly outperforms competitive baselines ... including real-world web navigation" (no numbers in the abstract) — [arXiv 2403.08978](https://arxiv.org/abs/2403.08978)
- **AutoManual** (Chen et al., arXiv:2405.16247, NeurIPS 2024). Agents build a rule manual online; evaluated mainly on ALFWorld (97.4% with GPT-4-turbo), not on realistic websites — [arXiv 2405.16247](https://arxiv.org/abs/2405.16247)
- **ExpeL** (Zhao et al., arXiv:2308.10144, AAAI 2024). Gathers experiences on training tasks, extracts natural-language insights, recalls them at inference; abstract gives no web-navigation numbers — [arXiv 2308.10144](https://arxiv.org/abs/2308.10144)
- **Learn-by-interact** (Su et al., arXiv:2501.10893). Synthesizes trajectories from documentation, relabels them ("backward construction"), and uses them for retrieval-based ICL or fine-tuning; "improved by up to 12.2% for ICL with Claude-3.5" across SWE-bench, WebArena, OSWorld, Spider2-V — [arXiv 2501.10893](https://arxiv.org/abs/2501.10893)
- **Contextual Experience Replay (CER)** (Liu, Si, Narasimhan, Yao, arXiv:2506.06698, ACL 2025). Distils "environment dynamics" and "skills" from past trajectories into a buffer replayed in context; 36.7% WA ("relatively improving ... the GPT-4o agent baseline by 51.0%"), 31.9% VWA. In the offline setting the trajectories came from people asked "to navigate the website for three hours and design a few tasks", then annotated — [arXiv 2506.06698](https://arxiv.org/abs/2506.06698)
- **ReasoningBank** (Ouyang et al., arXiv:2509.25140, ICLR 2026; code under google-research on GitHub per the arXiv comment). Distils strategies from self-judged successes and failures; "up to 20% relative improvement" and "up to 16% fewer interaction steps" on WebArena, Mind2Web, SWE-Bench-Verified — [arXiv 2509.25140](https://arxiv.org/abs/2509.25140)
- **WebCoach** (Liu et al., arXiv:2511.12997). Cross-session episodic memory with a "Coach" that injects advice; on WebVoyager with a 38B model "increases task success rates from 47% to 61% while reducing or maintaining the average number of steps" — [arXiv 2511.12997](https://arxiv.org/abs/2511.12997)
- **Agentic Plan Caching** (Zhang, Wornow, Wan, Olukotun, arXiv:2506.14852, NeurIPS 2025). Caches plan templates keyed by an LLM-extracted intent keyword and adapts them with a small model; "reduce costs by 50.31% and latency by 27.28% on average while maintaining 96.61% of optimal accuracy". Evaluated on FinanceBench, QASPER, TabMWP, AIME and GAIA, not on GUI or web-navigation benchmarks. Query-similarity matching produced "a high number of false positives ... or false negatives", so exact keyword match is used. Stated limit: "for highly dynamic workloads with frequent task variations, the benefits of caching may diminish" — [arXiv 2506.14852](https://arxiv.org/abs/2506.14852)
- **AgentRR** (Feng et al., arXiv:2505.17716). A design paper (with a case study, no benchmark numbers) proposing record, summarize into "multi-level experiences", and replay guarded by "check functions"; lists "User Record, Model Replay" as an application mode and names open challenges of "experience completeness, replay robustness, generalization" — [arXiv 2505.17716](https://arxiv.org/abs/2505.17716)

#### 2.3 Exploration and synthetic experience (mostly used for training, not inference-time memory)
- **BAGEL** (Murty et al., arXiv:2403.08140, ICML 2024): converts random exploration into demonstrations by iterative relabeling; "improvements of over 2-13% absolute on ToolQA and MiniWob++, with up to 13x reduction in execution failures" — [arXiv 2403.08140](https://arxiv.org/abs/2403.08140)
- **NNetNav** (Murty et al., arXiv:2410.02907): unsupervised exploration with hindsight labeling and pruning; Llama-3.1-8b fine-tuned on 10k self-generated demonstrations reaches "over 16% success rate on WebArena, and 35% on WebVoyager" — [arXiv 2410.02907](https://arxiv.org/abs/2410.02907)
- **PAE** (Zhou et al., arXiv:2412.13194): a task proposer (given "user demos or even just the name of the website"), an agent, and a VLM evaluator generate RL signal for skill discovery on WebVoyager/WebArena sites — [arXiv 2412.13194](https://arxiv.org/abs/2412.13194)
- **OS-Genesis** (Sun et al., arXiv:2412.19723, ACL 2025): agents interact first, then tasks are derived retrospectively ("reverse task synthesis") with a trajectory reward model, for training GUI agents — [arXiv 2412.19723](https://arxiv.org/abs/2412.19723)
- **Explorer** (Pahuja et al., arXiv:2502.11357, ACL 2025 Findings): "over 94K successful multimodal web trajectories, spanning 49K unique URLs"; "average cost is 28 cents per successful trajectory" — [arXiv 2502.11357](https://arxiv.org/abs/2502.11357)
- **AgentTrek** (Xu et al., arXiv:2412.09605, ICLR 2025 Spotlight): replays web tutorials with a VLM agent to synthesize trajectories at "$0.55 per high-quality trajectory" — [arXiv 2412.09605](https://arxiv.org/abs/2412.09605)
- **WebDreamer** (Gu et al., arXiv:2411.06559): uses an LLM as a world model to simulate candidate actions; "competitive, while being 4-5 times more efficient, with tree search"; motivated by the fact that "real-world environments such as the web are rife with irreversible actions" — [arXiv 2411.06559](https://arxiv.org/abs/2411.06559)
- **WMA** (Chae et al., arXiv:2410.13232, ICLR 2025): trains a transition-focused world model; reports cost and time efficiency over tree search "by 6.8x and 5.3x" — [arXiv 2410.13232](https://arxiv.org/abs/2410.13232)
- A paper titled "WebExplorer: Explore and Evolve for Training Long-Horizon Web Agents" (Liu et al., arXiv:2509.06501) exists; I verified the record only and did not review its content — [arXiv 2509.06501](https://arxiv.org/abs/2509.06501)

#### 2.4 UI transition graphs and app memory on Android
- **AutoDroid** (Wen et al., arXiv:2308.15272, MobiCom 2024). Acquisition: "explores the app by randomly clicking buttons on the screen and records the result in a UI Transition Graph (UTG) memory"; an LLM then summarizes a "simulated task" per UI element. "For every app, it takes about 0.5-1 hour to generate the UI Transition Graph (UTG)", plus 5–10 minutes of LLM summarization. Use: the k most similar simulated tasks and their UI paths are retrieved into the prompt; very similar tasks can be executed from memory "without calling LLM". Results: action accuracy 90.9%, task completion 71.3% on 158 DroidTask tasks. Memory ablation (Fig. 8, values not given in text): "the improvement in overall completion rate is much higher than the improvement in single-step accuracy ... smaller models benefit more from the inclusion of memory" — [arXiv 2308.15272](https://arxiv.org/abs/2308.15272)
- **AutoDroid-V2** (Wen et al., arXiv:2412.18116). Builds an app document automatically, then an on-device small model writes one multi-step script per task instead of one action per step; "10.5%-51.7% higher task completion rate than baselines, reducing runtime input and output token consumption by 43.5x and 5.8x, reducing LLM inference latency by 5.7-13.4×" — [arXiv 2412.18116](https://arxiv.org/abs/2412.18116)
- **MobileGPT** (Lee et al., arXiv:2312.03003). Acquisition: offline "random explorer" plus "user trace monitor" to visit screens ("50 unique app pages for each app, which typically took between 10 to 15 minutes", covering "89.65% (104 out of 116) of the total app pages required"); pages "unsuitable for random exploration (e.g., payment page)" are handled manually; then learning on first execution. Stored: a graph of screens with sub-tasks and parameterized action sequences. Use: on repeat ("warm start") tasks most actions come from memory. Results: 82.7% on new tasks; 98.75% on repeats; warm-start latency and cost down "62.5% and 68.8%" vs a GPT-4 baseline; memory hit rates of 70.6–98.6% at warm start (Table 3). "tasks that would take just over 30 seconds for a human could take more than two minutes for an LLM, and cost over a dollar". Recall is not purely mechanical: "out of 327 primitive actions, 53 actions (16.2%) were not adaptable through attribute-based adaptation and therefore required in-context adaptation via LLM". Stated failure causes for rule-based replay: target UI lacks key attributes, "multiple UIs could share the same attributes", "UIs may change unexpectedly with app updates". Includes a human-in-the-loop repair mode evaluated with 23 participants — [arXiv 2312.03003](https://arxiv.org/abs/2312.03003)
- **AppAgent** (Zhang et al., arXiv:2312.13771, CHI 2025): "learns to navigate and use new apps either through autonomous exploration or by observing human demonstrations", which "generates a knowledge base that the agent refers to" — [arXiv 2312.13771](https://arxiv.org/abs/2312.13771)
- **AppAgentX** (Jiang et al., arXiv:2503.02268). Records execution history as a chain of page/element nodes and evolves "shortcut" high-level actions that replace repeated sequences; falls back to basic actions when a shortcut does not match. Table 1: chain memory lifts SR from 16.9% to 70.8%; shortcuts cut steps "from 9.1 to 5.7", step time "from 23 to 16 seconds", tokens "from 9.26k to 4.94k". The DMI paper criticizes it for "reliance on visual element matching" — [arXiv 2503.02268](https://arxiv.org/abs/2503.02268); [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2)
- **KG-RAG** (Guan et al., arXiv:2509.00366, EMNLP 2025). Converts UTGs into a vector database and retrieves navigation paths; "75.8% success rate (8.9% improvement over AutoDroid) ... reducing average task steps from 4.5 to 4.1"; "a UTG cost ablation shows accuracy saturates at ~4h per complex app" — [arXiv 2509.00366](https://arxiv.org/abs/2509.00366)
- **PG-Agent** (Chen et al., arXiv:2509.03536, ACM MM 2025): converts sequential episodes into page graphs and retrieves guidelines from them — [arXiv 2509.03536](https://arxiv.org/abs/2509.03536)
- **GUI-explorer** (Xie et al., arXiv:2505.16827, ACL 2025): autonomous exploration then unsupervised mining of (observation, action, outcome) "transition-aware knowledge"; 53.7% on SPA-Bench, 47.4% on AndroidWorld, no parameter updates — [arXiv 2505.16827](https://arxiv.org/abs/2505.16827)
- **GUI-Xplore** (Sun et al., arXiv:2503.17709, CVPR 2025): a dataset with pre-recorded exploration videos per app; Xplore-Agent builds a GUI transition graph from the video and gains "10% improvement over existing methods in unfamiliar environments" — [arXiv 2503.17709](https://arxiv.org/abs/2503.17709)
- **LLM-Explorer** (Zhao et al., arXiv:2505.10593, MobiCom 2025): uses the LLM to maintain compact app knowledge rather than to choose every action; "fastest and highest coverage among all automated app explorers, with over 148x lower cost than the state-of-the-art LLM-based approach" — [arXiv 2505.10593](https://arxiv.org/abs/2505.10593)
- **Agent-SAMA** (Guo et al., arXiv:2505.23596, AAAI 2026): builds a finite-state machine of screens and transitions at run time and uses it for verification and recovery; "84.0% success rate and a 71.9% recovery rate" on Mobile-Eval-E — [arXiv 2505.23596](https://arxiv.org/abs/2505.23596)
- **Mobile-Agent-E** (Wang et al., arXiv:2501.11733): long-term memory of "Tips" and executable "Shortcuts"; "22% absolute improvement over previous state-of-the-art" on its own benchmark — [arXiv 2501.11733](https://arxiv.org/abs/2501.11733)

#### 2.5 Desktop: UFO / UFO2, Agent S, AXIS
- **UFO2** (Zhang et al., Microsoft, arXiv:2504.14603; the baseline used by DMI). Its knowledge substrate is "a retrieval-augmented memory that integrates documentation and historical execution logs"; "versioned indexing ensures that knowledge artifacts can evolve alongside software updates". "Speculative multi-action execution consolidates multiple steps into a single LLM call, lowering inference cost by up to 51.5%", validating predicted actions "using lightweight control-state checks" — [arXiv 2504.14603](https://arxiv.org/abs/2504.14603)
- **UFO** (Zhang et al., arXiv:2402.07939): the earlier Windows UI agent from the same group (record verified; content not re-read here) — [arXiv 2402.07939](https://arxiv.org/abs/2402.07939)
- **Agent S** (Agashe et al., arXiv:2410.08164, ICLR 2025). "Experience-augmented hierarchical planning" with web search, narrative memory (full-task experiences) and episodic memory (sub-task experiences), seeded by self-supervised exploration. Ablation on a 65-task OSWorld subset with GPT-4o (Table 2): full 26.15%; without web knowledge 16.80%; without narrative memory 21.41%; without episodic memory 18.46%; without all 13.85%; baseline 10.77% — [arXiv 2410.08164](https://arxiv.org/abs/2410.08164)
- **Agent S2** (Agashe et al., arXiv:2504.00906) focuses on mixture-of-grounding and proactive hierarchical planning; the follow-up "Scaling Agents for Computer Use" (arXiv:2510.02250) reaches 72.6% on OSWorld by running multiple rollouts and judging them ("Behavior Judge"), i.e. by spending more compute, not less — [arXiv 2504.00906](https://arxiv.org/abs/2504.00906); [arXiv 2510.02250](https://arxiv.org/abs/2510.02250)
- **AXIS** (Lu et al., arXiv:2409.17140): explores an app to wrap UI traces as APIs and prefers API calls over UI steps; on Word "reduces task completion time by 65%-70% and cognitive workload by 38%-53%, while maintaining accuracy of 97%-98% compared to humans" — [arXiv 2409.17140](https://arxiv.org/abs/2409.17140)

#### 2.6 Classic GUI modeling and web crawling (software engineering)
- **GUI ripping**: Memon, Banerjee, Nagarajan, "GUI ripping: reverse engineering of graphical user interfaces for testing", WCRE 2003, pp. 260–269 — [Crossref record](https://api.crossref.org/works/10.1109/WCRE.2003.1287256). **GUITAR**: Nguyen, Robbins, Banerjee, Memon, Automated Software Engineering 21(1):65–105 — [Crossref record](https://api.crossref.org/works/10.1007/s10515-013-0128-9)
- How DMI characterizes this lineage: state can be restored "by restarting the application after every interaction (Memon et al., 2003), [but] this incurs a prohibitive time cost"; "Early Win32 GUITAR ... expands multi-source graphs into multiple trees by cloning subgraphs to ensure unique paths; whereas modern, large UIs trigger exponential node growth." — [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2)
- **Crawljax**: Mesbah, van Deursen, Lenselink, "Crawling Ajax-Based Web Applications through Dynamic Analysis of User Interface State Changes", ACM TWEB 6(1), 2012. Abstract: Ajax techniques "shatter the concept of webpages with unique URLs, on which traditional Web crawlers are based"; the algorithm "scans the DOM tree, spots candidate elements that are capable of changing the state, fires events on those candidate elements, and incrementally infers a state machine" — [Crossref record](https://api.crossref.org/works/10.1145/2109205.2109208)
- **Near-duplicate states**: Yandrapally, Stocco, Mesbah, "Near-duplicate detection in web app model inference", ICSE 2020, pp. 186–197 — [Crossref record](https://api.crossref.org/works/10.1145/3377811.3380416). **FragGen** (Yandrapally & Mesbah, IEEE TSE, arXiv:2110.14043): "existing model inference techniques rely on threshold-based whole-page comparison to establish state equivalence, which cannot reliably identify near-duplicate web pages in modern web apps"; threshold selection is "a manual tedious fine-tuning process"; fragment-based abstraction "detected 123% more near-duplicates", with inferred models having "62% more precision and 70% more recall on average"; generated test actions have "nearly 100% success rate on the same version of the web app" — [arXiv 2110.14043](https://arxiv.org/abs/2110.14043)
- **WebExplor** (Zheng et al., arXiv:2103.06018; publication venue not verified here): curiosity-driven RL that incrementally builds an automaton during exploration. Named difficulties: "dynamic content update and deep bugs hiding under complicated user interactions and specific input values"; random approaches "often create invalid test cases" and "some hard-to-reach web pages may never be explored"; "long sequences of actions ... are often needed to complete certain tasks such as filling in and submitting forms"; dynamic content "cannot be easily captured by the static navigation models" — [arXiv 2103.06018](https://arxiv.org/abs/2103.06018)
- **QExplore**: Sherin, Muqeet, Khan, Iqbal, "QExplore: An exploration strategy for dynamic web applications using guided search", Journal of Systems and Software 195, 2023 (bibliographic record only; content not reviewed) — [Crossref record](https://api.crossref.org/works/10.1016/j.jss.2022.111512)

#### 2.7 Robust element identification across UI changes
- **Similo** (Nass, Alégroth, Feldt, Leotta, Ricca, ACM TOSEM 32(3), 2023). Weighted similarity over multiple locator parameters; on 48 popular websites, old version vs newer version, "it failed to locate the correct target web element in 91 out of 801 considered cases (i.e., 11%) compared to 214 failed cases (i.e., 27%) for the baseline approach"; "average time to locate a web element was determined to be 4 milliseconds" — [Crossref record](https://api.crossref.org/works/10.1145/3571855)
- **VON Similo** (Nass, Coppola, Alégroth, Feldt, arXiv:2301.03863, ICST 2023 per my recollection; venue not verified here). Treats visually overlapping DOM nodes as one target; "94.7% accuracy in identifying a web element in a new release of the same SUT. In comparison, Similo provides 83.8% accuracy." — [arXiv 2301.03863](https://arxiv.org/abs/2301.03863)
- **VON Similo LLM** (Nass, Alégroth, Feldt, arXiv:2310.02046). GPT-4 re-ranks the top-10 similarity candidates; "reducing failed localizations from 70 to 40 (out of 804), a 43% reduction", "Despite its slower execution time and additional costs of using the GPT-4 model" — [arXiv 2310.02046](https://arxiv.org/abs/2310.02046)
- **Robula+**: Leotta, Stocco, Ricca, Tonella, "Robula+: an algorithm for generating robust XPath locators for web testing", J. Software: Evolution and Process 28(3):177–204, 2016 (bibliographic record only) — [Crossref record](https://api.crossref.org/works/10.1002/smr.1771)

#### 2.9 Plan-then-execute versus step-by-step
- **Plan-and-Act** (Erdogan et al., arXiv:2503.09572, ICML 2025). A planner writes a high-level plan and an executor grounds it. A static plan was not enough: "it struggled with tasks requiring analysis of dynamic content"; adding dynamic replanning after each step "significantly increases the performance of the model by 10.31% over the static Planner, achieving 53.94% accuracy on WebArena-Lite" (57.58% in the best configuration; 81.36% on WebVoyager, text-only). An un-grounded planner can hurt: "since the Planner is not trained on data that is grounded to these specific websites, these plans are suboptimal and can confuse the Executor" — [arXiv 2503.09572](https://arxiv.org/abs/2503.09572)
- One-shot planning over an explicit app model works when execution is deterministic and verified: ActionEngine (1.5–3.5 calls vs 7–16), with search-dependent tasks as the stated boundary — [arXiv 2602.20502](https://arxiv.org/abs/2602.20502); DMI (4.61 vs 8.16 calls) with forced stop-and-observe before composite interactions — [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2); UFO2 speculative multi-action with control-state checks (up to 51.5% lower inference cost) — [arXiv 2504.14603](https://arxiv.org/abs/2504.14603); AutoDroid-V2 one script per task (5.7–13.4× lower inference latency) — [arXiv 2412.18116](https://arxiv.org/abs/2412.18116)
- Compound actions that hide partial state changes: WebChallenger's rule is that sequences "whose intermediate steps produce only partial state changes to the current page (dropdown expansion, search suggestions, field-by-field form entry) are collapsed into a single compound action ... while actions that navigate to a different page are kept as individual agent actions"; removing them raised steps from 7.20 to 9.85 — [arXiv 2606.10423](https://arxiv.org/abs/2606.10423)
- Where pre-determined sequences go stale: AWM's workflow-as-action executes "without seeing the intermediate states" and fails on pop-ups — [arXiv 2409.07429](https://arxiv.org/abs/2409.07429); DMI's Challenge #3 ("unexpected intermediate outcomes can invalidate subsequent steps") — [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2); Agentic Plan Caching's "highly dynamic workloads" caveat — [arXiv 2506.14852](https://arxiv.org/abs/2506.14852)
- Alternative to UI navigation altogether: "Beyond Browsing: API-Based Web Agents" (Song et al., arXiv:2410.16464) reports a hybrid browsing+API agent at 38.9% on WebArena, "more than 24.0% absolute improvement over web browsing alone"; **SteP** (Sodhi et al., arXiv:2310.03720) reached 33.5% on WebArena with hand-written per-site policies; **AgentOccam** (Yang et al., arXiv:2410.13825) gained 26.6 points over a plain agent purely by refining the observation and action space, "without using in-context examples, new agent roles, online feedback or search strategies" — [arXiv 2410.16464](https://arxiv.org/abs/2410.16464); [arXiv 2310.03720](https://arxiv.org/abs/2310.03720); [arXiv 2410.13825](https://arxiv.org/abs/2410.13825)
- Declarative, site-provided interfaces: **VOIX** (Schultze et al., arXiv:2511.11287) proposes `<tool>` and `<context>` HTML elements so the site developer declares actions and state; evaluated for developer practicality in "a three-day hackathon study with 16 developers", not for agent success or speed. "Build the web for agents, not agents for the web" (Lù et al., arXiv:2506.10953) is a position paper arguing for agent-specific web interfaces — [arXiv 2511.11287](https://arxiv.org/abs/2511.11287); [arXiv 2506.10953](https://arxiv.org/abs/2506.10953)

#### 2.10 Guiding humans through UIs (HCI)
- **Guided vs automated copilots** (Khurana, Su, Wang, Chilana, CHI 2025, arXiv:2504.15549). Within-subject study, N=20, Google Sheets and Figma. "GuidedCopilot" "automates only trivial or repetitive tasks while offering step-by-step visual guidance to help users locate UI elements"; "AutoCopilot" does the task. "None of the participants fully completed the tasks in Sheets or Figma using AutoCopilot. In contrast, with GuidedCopilot, 11/20 participants successfully completed the tasks in Sheets, and 6/20 completed the Figma tasks". Mean share of task completed in Sheets: "35.0% ... with AutoCopilot, compared to 88.5% ... with GuidedCopilot" (p<0.0001); in Figma 20.0% vs 55.0%. Task accuracy in Sheets 82.0% vs 12.0%. GuidedCopilot scored higher on "user control, software utility, and learnability", "while AutoCopilot saved time for simpler visual tasks". Friction reported: "some felt that it provided overly detailed instructions for already-familiar tasks, while others struggled to map visuals in the chat to the corresponding UI elements"; the follow-up design (N=10) embedded state-aware preview clips in the interface. Both copilots were built by the authors for the study's tasks — [arXiv 2504.15549](https://arxiv.org/abs/2504.15549)
- **Text-only LLM help** (Khurana, Subramonyam, Chilana, IUI 2024, arXiv:2402.08030). 16 participants, Excel and PowerPoint tasks. An LLM with software context and prompt guidelines gave more accurate guidance than baseline ChatGPT (PowerPoint 64.4% vs 37.5%; Excel 65.7% vs 45%), yet "Most users struggled to understand how the prompt's text related to the LLM's responses and often followed the LLM's suggestions verbatim, even if they were incorrect ... leading to low task completion rates"; even the context-aware assistant "did not always provide specific and relevant instructions (for example, where to locate menu functions within the UI)" and users "remained unaware of inaccuracies" — [arXiv 2402.08030](https://arxiv.org/abs/2402.08030)
- **HelpViz** (Zhong, Li, Chi, Li, UIST 2021, arXiv:2108.03356). Executes text instructions on emulators to produce contextual visual tutorials that track progress and highlight the next step; in a 10-participant evaluation "participants preferred tutorials generated by HelpViz over text-based instructions". Notes that "As software is frequently updated, a tutorial needs to be constantly revised" — [arXiv 2108.03356](https://arxiv.org/abs/2108.03356)
- **CowPilot** (Huq et al., NAACL 2025 demo, arXiv:2501.16609). The agent proposes next steps and the human can pause, reject or take over; in case studies on five websites "the human-agent collaborative mode achieves the highest success rate of 95% while requiring humans to perform only 15.2% of the total steps" — [arXiv 2501.16609](https://arxiv.org/abs/2501.16609)
- **MobileGPT's human-in-the-loop repair** was evaluated with 23 participants; corrected executions are what get stored, which the authors credit for 98.75% warm-start accuracy — [arXiv 2312.03003](https://arxiv.org/abs/2312.03003)
- Classic systems verified to exist (bibliographic records only; findings not verified in this session): Kelleher & Pausch, "Stencils-based tutorials", CHI 2005, pp. 541–550 — [Crossref record](https://api.crossref.org/works/10.1145/1054972.1055047); Palmiter & Elkerton, "An evaluation of animated demonstrations of learning computer-based tasks", CHI '91, pp. 257–263 — [Crossref record](https://api.crossref.org/works/10.1145/108844.108906); Bergman, Castelli, Lau, Oblinger, "DocWizards", UIST 2005, pp. 191–200 — [Crossref record](https://api.crossref.org/works/10.1145/1095034.1095067); Leshed, Haber, Matthews, Lau, "CoScripter", CHI 2008, pp. 1719–1728 — [Crossref record](https://api.crossref.org/works/10.1145/1357054.1357323); Chilana, Ko, Wobbrock, "LemonAid", CHI 2012, pp. 1549–1558 — [Crossref record](https://api.crossref.org/works/10.1145/2207676.2208620)

### Inferences
- The papers sort, imperfectly, by what the artifact is used for. "Read-only" knowledge (AWM text workflows, WebATLAS cognitive map, WebChallenger memory, CER, ReasoningBank, Agent S memory) moves SR by roughly 4–15 points and steps by 0–25% (AWM is the top of that range at 7.9 to 5.9; WebChallenger memory the bottom at 7.34 to 7.20). "Executable" knowledge spans a wider range: ASI −11% steps, WebNavigator −11 to −12%, WALT −27%, AppAgentX −37%, DMI −43.5%, ActionEngine 4–6× fewer LLM calls, MobileGPT −62.5% latency on repeats, AutoDroid-V2 5.7–13.4× lower inference latency. Every multi-fold reduction comes from an executable mechanism; no read-only memory paper reports one.
- WebNavigator shows that even an executable graph does not guarantee wall-clock savings: steps fell 11–12% but time per task was flat, because locating the target (retrieval plus an 11 s selector call) replaced the saved navigation steps and most time is spent in local execution on the destination page.
- Android results are the nearest thing to a "repeat-task" setting like help-desk questions: MobileGPT's 62.5% latency reduction is for the second execution of a task type, after a first execution that was no faster (cold start +3.9% latency).
- Almost all quantitative results are on benchmark replicas (WebArena family) or short lists of public sites; none of the papers evaluates a customer-specific logged-in SaaS application, which WALT states explicitly as untested.

### Gaps
- Result numbers for Stencils-based tutorials, Palmiter & Elkerton, DocWizards, CoScripter, LemonAid, Robula+, GUITAR and QExplore were not verified (ACM/Wiley/Elsevier pages were not accessible and the search budget was exhausted). From memory, Stencils is usually cited for faster tutorial completion with fewer errors than paper tutorials, and Palmiter & Elkerton for faster acquisition but weaker retention with animated demonstrations; the writer should treat both as unverified until checked against the papers.
- I found no controlled study (as of this search) that measures human task time or error rate for LLM-driven on-screen pointing ("click here") against text instructions in a live web app; Khurana et al. 2025 compares guidance against full automation, not against text-only help, and its visuals were shown in a chat panel.
- AutoGuide's and ExpeL's web-navigation numbers, AutoDroid's memory-ablation values (figure only) and SkillWeaver's step counts were not extracted.
- 2026 coverage: I located WebNavigator, ActionEngine, WebChallenger, OpAgent and WebCoach; other 2026 work on site graphs or plan caching for GUI agents may exist that one search pass did not surface.
- The official OSWorld-Verified and WebArena leaderboards were not read directly; numbers come from third-party trackers.

## Key question 1. Does putting a static site map in the prompt, by itself, make an agent faster or more accurate?

### Takeaway
By itself, no for speed and "sometimes, modestly" for accuracy. The only direct test (DMI §5.5) found no change in success or steps for a strong model and a small gain for a weak one; other papers show a raw map can even hurt until it is summarized or retrieved selectively, and that read-only memory barely changes step counts.

### Cited Findings
- Direct test, strong model: navigation forest in the prompt, no declarative interface: SR 42.0% vs 44.4%, steps 8.41 vs 8.16 (normalized 8.58 vs 7.94); authors: "the declarative interface, not the static knowledge, is the primary source of DMI's effectiveness" — [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2)
- Direct test, weak model: GPT-5-mini SR 23.5% vs 17.3%, steps 6.32 vs 7.14; authors: "supplementary topology knowledge can be helpful for models with less general-purpose knowledge" — [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2)
- Same pattern on Android: "smaller models benefit more from the inclusion of memory" — [arXiv 2308.15272](https://arxiv.org/abs/2308.15272)
- A raw map can hurt: adding the raw-HTML cognitive map to AgentOccam lowered WA-Lite SR from 47.9% to 44.8%; the LLM-summarized map raised it to 57.4% — [arXiv 2510.22732](https://arxiv.org/abs/2510.22732)
- Read-only site memory changes accuracy more than speed: WebChallenger without memory loses 7.6 SR points but steps go only from 7.20 to 7.34 and tokens from 47.0M to 48.1M; on one site (Reddit) memory made no difference — [arXiv 2606.10423](https://arxiv.org/abs/2606.10423)
- Whole-graph-in-prompt is treated as impractical by the web graph papers: "Directly providing the complete Interaction Graph G to LLMs is impractical due to context window constraints" (WebNavigator uses retrieval of top-30 candidates plus a selector); DMI ships a pruned 15K–30K-token core with `further_query` rather than the full forest — [arXiv 2603.20366](https://arxiv.org/abs/2603.20366); [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2)
- Text workflows in the prompt (not a site map, but also read-only knowledge) did help both metrics moderately: AWM 35.5% vs 23.5% SR and 5.9 vs 7.9 steps — [arXiv 2409.07429](https://arxiv.org/abs/2409.07429)
- Plans not grounded in the specific site "are suboptimal and can confuse the Executor" — [arXiv 2503.09572](https://arxiv.org/abs/2503.09572)
- For human-facing guidance, domain context raised the accuracy of LLM instructions (64.4% vs 37.5% on PowerPoint tasks) but did not fix task completion, partly because the instructions did not say "where to locate menu functions within the UI" — [arXiv 2402.08030](https://arxiv.org/abs/2402.08030)
- A static link crawl is not the artifact these papers use: "Traditional crawlers parse static hyperlinks to discover URL-addressable pages but miss interaction-triggered states" (WebNavigator); Ajax "shatter[s] the concept of webpages with unique URLs, on which traditional Web crawlers are based" (Crawljax) — [arXiv 2603.20366](https://arxiv.org/abs/2603.20366); [Crossref record](https://api.crossref.org/works/10.1145/2109205.2109208)

### Inferences
- The product's current design (site map from a no-JS, no-login crawl, in the system prompt, one LLM call per step) is the configuration the DMI ablation found unhelpful for a strong model: knowledge present, mechanism unchanged. Expect at most an accuracy benefit on steps where the target is not inferable from the live DOM (the "which menu hides this?" decision), and more benefit the weaker/cheaper the model. This is an extrapolation from desktop-agent and benchmark-web results to a human-guided product.
- In the product the live DOM already supplies the current page's elements, so the marginal information in a site map is only about pages and states the user is not on. That is exactly the "controls not yet visible" case where DMI's gain came from, but DMI captured it by acting on it without further LLM calls, not by reading it.
- Prompt length is a latency cost per call. DMI reports per-call latency "similar" with 15K–30K extra tokens on GPT-5, and higher on the small model; the product should measure this rather than assume it is free.

### Gaps
- No paper tests "site map in prompt" on a guide-the-human loop, or reports time-to-first-token effects of a large static prompt with provider-side prompt caching.
- No paper compares a hyperlink-only site map against an interaction graph as prompt knowledge.

## Key question 2. Which mechanisms actually cut LLM calls per task, and what offline artifact does each need?

### Takeaway
Four mechanisms have measured reductions in LLM calls: deterministic pathfinding over a navigation graph, replay of cached parameterized sub-tasks, compiled skills/tools, and one-shot program synthesis over an application state machine. Each needs an artifact that is executable against the live UI: stable element locators plus transitions, not just page descriptions.

### Cited Findings

| Mechanism | Offline artifact required | Measured effect on calls / time | Effect on success | Source |
|---|---|---|---|---|
| Declarative access: LLM names target control(s), executor navigates | Full control-level navigation graph, de-cycled to a forest with unique paths; per-control identifiers; fuzzy matcher | 8.16 to 4.61 LLM calls (−43.5%); time −39%; >61% of successes in 4 calls incl. 3 fixed | 44.4% to 74.1% | [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2) |
| Retrieve target page, then "teleport" along shortest path | Interaction graph of page states with XPath-grounded edges; screenshot embeddings; selector LLM | Steps 10.10 to 8.98 and 10.14 to 8.93 (−11 to −12%), multi-site −19 to −28%; wall-clock unchanged; tokens per task 67,351 to 123,684 | 50.4% to 63.3% (Gemini 2.5 Pro) | [arXiv 2603.20366](https://arxiv.org/abs/2603.20366) |
| One-shot program over a state-machine memory, deterministic execution, reactive patcher | Per-app state machine: states, operations with validated locators, inputs/outputs, transitions | 7–16 calls to 1.5–3.5; 87 s to 27 s; $0.40 to $0.05 per task | 82.7% to 91.2% (73.1% with crawler-only memory) | [arXiv 2602.20502](https://arxiv.org/abs/2602.20502) |

- Even with an executable artifact, the LLM is still needed for the semantic choice: WebNavigator's retrieval top-1 accuracy is only 22.97–63.83% and needs an LLM selector (75.82–96.72%); Agentic Plan Caching found query-similarity lookup unreliable — [arXiv 2603.20366](https://arxiv.org/abs/2603.20366); [arXiv 2506.14852](https://arxiv.org/abs/2506.14852)
- Agents under-use tools that are merely offered: workflow actions called in "merely 18.5% of the tasks" (AWM); "the agent fails to call this API during the task execution" (SkillWeaver) — [arXiv 2409.07429](https://arxiv.org/abs/2409.07429); [arXiv 2504.07079](https://arxiv.org/abs/2504.07079)
- Path ambiguity is real: the same control reached by different paths can mean different things (DMI's colour-picker example), which is why DMI keeps unique paths and criticizes greedy nearest-path matching in AutoDroid-style graphs — [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2)

### Inferences
- Mapping to the product, where the human executes every click: the number of human steps is fixed by the UI path, so the saving available is LLM calls per human step. A graph with stable element identifiers allows "one LLM call to choose the destination, zero LLM calls for intermediate pointers" (DMI/WebNavigator/ActionEngine pattern). A per-goal cache of successful trajectories allows "zero or one small-model call on a cache hit" (MobileGPT/plan-caching pattern). Parameterized skills matter less when a human types the values. These are my transfers; no paper measures them with a human executor.
- The minimum viable artifact for skipping calls is therefore: for each transition, a robust locator for the element to click, an identifier or signature for the resulting state, and a check that the live DOM is in the expected state. A list of page headings and link labels (the current crawl) lacks the state signature and the interaction-triggered states.
- Because each step waits for a human, the system gets a free verification point after every click (the settled DOM). That removes the main risk of one-shot plans in autonomous agents (acting on stale assumptions without observing), and resembles DMI's forced stop-and-observe rule.

### Gaps
- No measurement of cache-hit rates for real end-user help questions in a SaaS app; MobileGPT's hit rates are for scripted repeat tasks.
- No paper reports the end-to-end latency a person perceives per step when intermediate pointers are served from a graph.

## Key question 3. How is the artifact best acquired for a logged-in, JavaScript-rendered web app, and what does each route need from the app owner?

### Takeaway
The literature supports automated interaction-level exploration in an authenticated browser as the way to get a navigation graph (tens of minutes to a few hours per app, zero to tens of dollars), but every system needs owner-supplied or hand-tuned inputs: a session or test account, a blocklist of destructive or external actions, seeded data so conditional UI appears, and a refinement pass. Learning from real executions gives the highest-precision reusable paths but needs a correctness signal; human demonstrations gave the best tools in the one head-to-head comparison.

### Cited Findings

**Route A: offline automated exploration**
- Deterministic, LLM-free crawlers exist for JS-rendered sites: WebNavigator's adaptive BFS (2.1–316.8 min per WebArena domain on CPU; about $0.90 for the largest) and WebChallenger's depth-first traversal (limits: 75 elements/page, 500 pages, depth 2, 12 h timeout) — [arXiv 2603.20366](https://arxiv.org/abs/2603.20366); [arXiv 2606.10423](https://arxiv.org/abs/2606.10423)
- LLM-driven crawlers cost more but capture operations and descriptions: ActionEngine 36–260 min and $11.6–$37.2 per app; SkillWeaver 160 GPT-4o iterations per site; AutoDroid 0.5–1 h plus 5–10 min of LLM summarization; KG-RAG "accuracy saturates at ~4h per complex app"; MobileGPT 10–15 min for 50 screens covering 89.65% of needed pages — [arXiv 2602.20502](https://arxiv.org/abs/2602.20502); [arXiv 2504.07079](https://arxiv.org/abs/2504.07079); [arXiv 2308.15272](https://arxiv.org/abs/2308.15272); [arXiv 2509.00366](https://arxiv.org/abs/2509.00366); [arXiv 2312.03003](https://arxiv.org/abs/2312.03003)
- Desktop reference point: DMI needed "< 3 hours" automated plus "around 1.5 person-days" of manual effort per app, mostly the blocklist — [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2)
- Everyone needs a blocklist or exclusions: DMI ("manual blocklist" for external transitions and unexitable states); WebNavigator ("configurable block list to exclude hazardous operations and external links"); SkillWeaver's prompt ("Do not interact with login/logout/user accounts"); MobileGPT (pages "unsuitable for random exploration (e.g., payment page)" explored manually) — [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2); [arXiv 2603.20366](https://arxiv.org/abs/2603.20366); [arXiv 2504.07079](https://arxiv.org/abs/2504.07079); [arXiv 2312.03003](https://arxiv.org/abs/2312.03003)
- State-dependent UI needs seeded context: DMI's context manager ("We manually instantiate representative objects ... Omitting it would compromise the completeness of the UNG"); ActionEngine ("sparse application data or insufficient interaction coverage may prevent the crawler from activating a control that reveals a hidden dialog"); SkillWeaver could not verify a skill because it lacked real collaborator emails as test input — [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2); [arXiv 2602.20502](https://arxiv.org/abs/2602.20502); [arXiv 2504.07079](https://arxiv.org/abs/2504.07079)
- State must be reset between probes: DMI relies on Esc/Close and avoids restart-per-action because of "prohibitive time cost"; WebChallenger restores state "by reloading the pre-click URL" — [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2); [arXiv 2606.10423](https://arxiv.org/abs/2606.10423)
- Click-only exploration was sufficient for navigation coverage in one controlled test (16/16 entry points on WA-Reddit at depth 3; typing into inputs added only search-result and form states) — [arXiv 2603.20366](https://arxiv.org/abs/2603.20366)
- State equivalence is the hard modeling problem on the web: threshold-based whole-page comparison "cannot reliably identify near-duplicate web pages"; FragGen's fragment-based abstraction improved model precision by 62% and recall by 70%. WebNavigator hashes DOM structure plus URL; WebChallenger matches list pages against templates and explores only one item per list — [arXiv 2110.14043](https://arxiv.org/abs/2110.14043); [arXiv 2603.20366](https://arxiv.org/abs/2603.20366); [arXiv 2606.10423](https://arxiv.org/abs/2606.10423)
- Crawler output needs a refinement pass against real tasks: ActionEngine's crawler-only memory gave 73.1% and refinement added 18.1 points, mostly by fixing selectors, adding waits and enriching descriptions; WebNavigator's SR on WA-Reddit rose 63.2% to 75.5% with exploration depth 1 to 4 — [arXiv 2602.20502](https://arxiv.org/abs/2602.20502); [arXiv 2603.20366](https://arxiv.org/abs/2603.20366)
- WebNavigator's authors see the app owner as the natural operator: "We plan to address this by developing a dedicated SDK for web developers that automates graph construction and maintenance" — [arXiv 2603.20366](https://arxiv.org/abs/2603.20366)

**Route B: learning from executed trajectories (agent runs or real sessions)**
- Online induction from the agent's own runs works without labels but inherits errors: AWM ("can lead to incorrect workflows"); ASI accepts only 15.6% of induced programs after execution-based verification; ReasoningBank and CER rely on an LLM judge to label success — [arXiv 2409.07429](https://arxiv.org/abs/2409.07429); [arXiv 2504.06821](https://arxiv.org/abs/2504.06821); [arXiv 2509.25140](https://arxiv.org/abs/2509.25140); [arXiv 2506.06698](https://arxiv.org/abs/2506.06698)
- Storing human-corrected executions gives near-perfect recall on repeats (MobileGPT 98.75%), and MobileGPT's offline stage already uses a "user trace monitor" alongside the random explorer — [arXiv 2312.03003](https://arxiv.org/abs/2312.03003)
- Page graphs can be built from recorded episodes rather than crawling (PG-Agent) — [arXiv 2509.03536](https://arxiv.org/abs/2509.03536)
- "User Record, Model Replay" is a named mode in AgentRR's design, with "check functions" as the trust anchor — [arXiv 2505.17716](https://arxiv.org/abs/2505.17716)

**Route C: human demonstrations**
- In WALT's ablation, tools built from author demonstrations gave the highest SR (66.0% vs 61.5% for auto-discovered tools on the same backbone) — [arXiv 2510.01524](https://arxiv.org/abs/2510.01524)
- AppAgent learns "by observing human demonstrations"; CER's offline setting used trajectories from people who explored each site for three hours; Synapse and ICAL build exemplar memories from human demonstrations (ICAL adds human feedback) — [arXiv 2312.13771](https://arxiv.org/abs/2312.13771); [arXiv 2506.06698](https://arxiv.org/abs/2506.06698); [arXiv 2306.07863](https://arxiv.org/abs/2306.07863); [arXiv 2406.14596](https://arxiv.org/abs/2406.14596)

**Route D: documentation**
- Documentation mainly improves the semantic choice, not navigation mechanics: Agent S loses the most when web knowledge is removed (26.15% to 16.80%); UFO2 indexes help documents and execution logs; Learn-by-interact and AgentTrek turn docs/tutorials into trajectories; DMI suggests augmenting the topology "with descriptions synthesized from documentation" — [arXiv 2410.08164](https://arxiv.org/abs/2410.08164); [arXiv 2504.14603](https://arxiv.org/abs/2504.14603); [arXiv 2501.10893](https://arxiv.org/abs/2501.10893); [arXiv 2412.09605](https://arxiv.org/abs/2412.09605); [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2)

### Inferences
- What onboarding would have to collect for Route A (synthesized from the requirements the papers state, not from any single paper): an authenticated test account or session per role; a deny-list of destructive, billing, messaging and external-link actions; seed data that makes conditional UI appear (an existing invoice, a second user, a connected integration); a depth/page budget; and a way to re-run the crawl on each release. The current plain-HTTP, no-login crawl collects none of the interaction-triggered states these systems rely on.
- The product has an asset the autonomous-agent papers lack: every guided session yields a human-executed click sequence in the real logged-in app, with the user's goal attached. That is Route B/C data at zero exploration cost and with real permissions, feature flags and data. Completion signals still need care (the papers needed judges or verification), and using end-user sessions raises privacy and consent questions the papers do not address.
- A hybrid seems best supported: crawl for the navigation skeleton and locators (cheap, LLM-free), refine and validate with a small set of owner-recorded demonstrations for high-value goals (WALT's upper bound, ActionEngine's warm-up), then keep correcting from live guided sessions (MobileGPT's repair-then-store).
- Role- and plan-dependent UI (different menus per permission) is a known gap in crawl-once designs; DMI's "version-specific" model and MobileGPT's per-device memory point to keying the artifact by app version and user role.

### Gaps
- None of the web papers reports crawling a multi-tenant SaaS app behind SSO, MFA, role-based menus or feature flags; WebArena sites are self-hosted replicas with fixed accounts.
- No paper quantifies how many recorded human sessions are needed before a goal-to-path cache covers most help requests.
- No head-to-head comparison of crawl-built versus session-built graphs on the same app.

## Key question 4. What are the known failure modes when a cached path meets a changed UI, and how do the papers detect and recover?

### Takeaway
The recurring failures are locator drift, renamed or conditional controls, states the crawl never saw, timing, and plans that assumed content they could not observe. Every system that executes cached paths pairs them with (1) tolerant element matching, (2) a per-step check against the live UI, (3) a fallback to step-by-step LLM reasoning, and, in the better ones, (4) writing the repair back into the memory.

### Cited Findings
- Renamed and conditional controls: "entering special text ... dynamically renames the 'Next' button to 'Go To'. Depth-first search exploration may miss such conditional changes, and without stable application identifiers, name changes break element matching"; topology/modeling inaccuracies were 4.8% of DMI's failures — [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2)
- Version specificity: DMI's model is "version-specific but reusable across machines for the same application build"; UFO2 uses "versioned indexing" of knowledge — [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2); [arXiv 2504.14603](https://arxiv.org/abs/2504.14603)
- Selector drift and volatile front-ends: "selector stabilization can drift after major redesigns"; "Highly dynamic interfaces, A/B experiments, CAPTCHAs, and heavy anti-automation can reduce determinism" (WALT); web "DOM structures and element attributes frequently change" (DMI §6) — [arXiv 2510.01524](https://arxiv.org/abs/2510.01524); [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2)
- Crawler-generated selectors can be wrong on day one: CSS selectors "that do not trigger the intended JavaScript event handlers"; missing waits for "AJAX grid refreshes" and "modal dialog animations" (ActionEngine) — [arXiv 2602.20502](https://arxiv.org/abs/2602.20502)
- Timing and transient IDs: "observations may be captured before a page has fully loaded"; injected element IDs "may become invalid by the time an action is executed" (WebNavigator) — [arXiv 2603.20366](https://arxiv.org/abs/2603.20366)
- Attribute-based replay fails when the target lacks key attributes, when "multiple UIs could share the same attributes", or after app updates; 16.2% of recalled actions needed an LLM to adapt (MobileGPT) — [arXiv 2312.03003](https://arxiv.org/abs/2312.03003)
- Blind sequences miss intermediate UI: AWM's book-flight workflow cannot handle pop-up choices; ActionEngine's planner "must choose search terms before observing the results"; Plan-and-Act's static planner "struggled with tasks requiring analysis of dynamic content" — [arXiv 2409.07429](https://arxiv.org/abs/2409.07429); [arXiv 2602.20502](https://arxiv.org/abs/2602.20502); [arXiv 2503.09572](https://arxiv.org/abs/2503.09572)
- Detection and recovery, DMI: fuzzy matcher over type, ancestor hierarchy and name similarity; retry for slow-loading controls; "structured error feedback" to the LLM; GUI primitives as "slow-path fallback" on "exceptions/unexpected UI states (e.g., error pop-ups)" — [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2)
- Detection and recovery, WebNavigator: selector may return None (3.6–9.1% of tasks) and the agent continues with low-level actions (43.6–62.2% still succeed); graph upkeep by a periodic verification traversal that "removes invalid nodes and edges" and explores from newly added DOM elements — [arXiv 2603.20366](https://arxiv.org/abs/2603.20366)
- Detection and recovery, ActionEngine: the Patcher "can inspect the current application with the GUI automation tool and re-ground the failed action" and "commits the repair back to the SMG so that subsequent tasks reuse the corrected operation"; after refinement "none of the observed failures are caused by broken selectors or structural deficiencies in the SMG" — [arXiv 2602.20502](https://arxiv.org/abs/2602.20502)
- Detection and recovery, WALT: validation failures are classified as "selector drift, uncovered enum values, timing issues, or semantic mismatches after URL promotion"; at run time an "agentic fallback ... spawns a fresh agent to handle a failing action script"; proposed future work is "Online tool patching when selectors and schemas drift" — [arXiv 2510.01524](https://arxiv.org/abs/2510.01524)
- Detection and recovery, mobile: MobileGPT falls back to in-context LLM adaptation using the stored example, then to human repair; AppAgentX "reverts to using actions from the basic action space" on shortcut mismatch; Agent-SAMA uses its FSM to detect unexpected results (recovery rate 71.9% on Mobile-Eval-E) — [arXiv 2312.03003](https://arxiv.org/abs/2312.03003); [arXiv 2503.02268](https://arxiv.org/abs/2503.02268); [arXiv 2505.23596](https://arxiv.org/abs/2505.23596)
- Cached page summaries are invalidated incrementally: "sections whose elements have changed since the last visit are re-summarized while unchanged sections retain" their summaries (WebChallenger) — [arXiv 2606.10423](https://arxiv.org/abs/2606.10423)
- How well tolerant matching works across real site revisions (testing literature): single-locator baseline fails 27% of 801 elements across versions of 48 sites; multi-attribute similarity (Similo) fails 11% at about 4 ms per lookup; adding visual-overlap grouping reaches 94.7% vs 83.8%; adding a GPT-4 re-rank over the top 10 cuts failures from 70 to 40 of 804 at extra time and cost — [Crossref record](https://api.crossref.org/works/10.1145/3571855); [arXiv 2301.03863](https://arxiv.org/abs/2301.03863); [arXiv 2310.02046](https://arxiv.org/abs/2310.02046)

### Inferences
- A workable recovery ladder for a pointer product, assembled from the above: (1) match the cached target by multiple attributes (role, accessible name, text, ancestor path, neighbours), not a single selector; (2) if confidence is high, point without an LLM call; (3) if ambiguous, send the top candidates to the LLM (the VON Similo LLM and WebNavigator selector pattern: verification is easier than generation); (4) if absent, fall back to the normal one-call-per-step loop with the cached path as a hint; (5) record the correction. Steps 1–2 are where latency is saved; steps 3–5 bound the damage.
- The testing literature's 5–27% per-element miss rates across site versions suggest a cached path of several steps will hit at least one mismatch fairly often after a UI release unless matching is multi-attribute; the product will need the fallback path to be routine, not exceptional. This is an extrapolation from homepage-element studies to app flows.
- For a human-facing pointer, a wrong cached pointer is a visible error (unlike an agent's silent retry), so the confidence threshold for skipping the LLM should be conservative; the papers do not study this cost asymmetry.
- Because the human's click produces a settled DOM before the next pointer, the product can verify state after every step for free, which is the main protection the autonomous one-shot planners lack.

### Gaps
- No paper reports longitudinal drift: how fast a web interaction graph goes stale under real release cadences, or the cost of WebNavigator-style periodic re-verification.
- No data on false-positive rates of multi-attribute matching inside dense SaaS UIs (tables of near-identical row actions), where "multiple UIs could share the same attributes".
- LLM-based locator repair has one small study (804 elements, GPT-4); newer self-healing-locator studies were not searched because the search budget ran out.

## Key question 5. What is NOT supported by evidence (claims the team should not make or rely on)?

### Takeaway
The literature does not support "memory of the site makes the guide fast" as stated. It supports a narrower claim: an executable model of the app, plus a mechanism that skips LLM calls and a fallback, makes autonomous agents need fewer calls on benchmark tasks; none of it has been measured on a human-guided product or a production SaaS app.

### Cited Findings
- Not supported: that knowledge in the prompt alone reduces steps or raises success for a strong model. DMI's own ablation: "no significant change in performance" — [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2)
- Not supported: reading "a single LLM call" as one call per task end to end. It is 4 calls with "a fixed 3-step overhead", on single-app Office tasks, with an executor doing the clicks; average successful-task time was still 239 s — [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2)
- Not supported: that DMI's approach is shown to work on the web. The authors call the browser "a canonical example" of UIs that resist pre-modeling and leave it to future work — [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2)
- Not supported: strong generalization from DMI's numbers. They come from 27 tasks × 3 runs in three Microsoft Office apps on Windows, one baseline framework, two models from one vendor; steps and time are computed on successful runs only — [arXiv HTML 2510.04607v2](https://arxiv.org/html/2510.04607v2)
- Not supported: that an offline graph makes tasks faster in wall-clock terms on the web. WebNavigator: +12.9 SR points but 753.5 s vs 773.6 s per task and more tokens; WebChallenger memory: +7.6 SR points, steps 7.34 to 7.20 — [arXiv 2603.20366](https://arxiv.org/abs/2603.20366); [arXiv 2606.10423](https://arxiv.org/abs/2606.10423)
- Not supported: quoting ActionEngine's 91.2% / 27 s as a general result. It is an arXiv preprint; the memory was refined on the benchmark's task templates; failures were manually re-adjudicated; crawler-only memory gave 73.1%; four of WebArena's domains only — [arXiv 2602.20502](https://arxiv.org/abs/2602.20502)
- Not supported: that a hyperlink crawl captures what these systems use. They explicitly go beyond static links to interaction-triggered states — [arXiv 2603.20366](https://arxiv.org/abs/2603.20366); [Crossref record](https://api.crossref.org/works/10.1145/2109205.2109208)
- Not supported: that learned skills/tools are reliably used once available. Workflow actions invoked in 18.5% of tasks; APIs not called; only 15.6% of induced programs verified — [arXiv 2409.07429](https://arxiv.org/abs/2409.07429); [arXiv 2504.07079](https://arxiv.org/abs/2504.07079); [arXiv 2504.06821](https://arxiv.org/abs/2504.06821)
- Not supported: that plan/trajectory caching has been validated for GUI navigation. Agentic Plan Caching was evaluated on document QA, math and GAIA; AgentRR offers a design and a case study — [arXiv 2506.14852](https://arxiv.org/abs/2506.14852); [arXiv 2505.17716](https://arxiv.org/abs/2505.17716)
- Not supported: that benchmark results transfer to enterprise apps. WALT: "broader external validity (e.g., enterprise apps) remains to be tested"; WebNavigator's and WebChallenger's live-site runs used only depth-1 exploration — [arXiv 2510.01524](https://arxiv.org/abs/2510.01524); [arXiv 2603.20366](https://arxiv.org/abs/2603.20366); [arXiv 2606.10423](https://arxiv.org/abs/2606.10423)
- Not supported: treating 2026 leaderboard numbers as reliability guarantees. Top WebVoyager and Online-Mind2Web rows are self-reported with custom judges and exclusions; the 2025 audit found most agents near 30% under human evaluation while reporting about 90% on WebVoyager, and showed 51% of sampled WebVoyager tasks solvable by a search-only shortcut — [steel.dev WebVoyager tracker](https://leaderboard.steel.dev/leaderboards/webvoyager.md); [steel.dev Online-Mind2Web tracker](https://leaderboard.steel.dev/leaderboards/online-mind2web.md); [arXiv 2504.01382](https://arxiv.org/abs/2504.01382)
- Not supported: that autonomous agents are fast. Reported per-task times range from 27 s (best case, programmatic) through 87–774 s on WebArena to "tens of minutes" on OSWorld and "up to 44 minutes" for Operator on hard live-web tasks — [arXiv 2602.20502](https://arxiv.org/abs/2602.20502); [arXiv 2603.20366](https://arxiv.org/abs/2603.20366); [arXiv 2506.16042](https://arxiv.org/abs/2506.16042); [arXiv 2504.01382](https://arxiv.org/abs/2504.01382)
- Not supported (by the HCI sources verified here): that on-screen guidance is faster than text or improves retention. Verified evidence is that step-by-step visual guidance beat full automation on completion, accuracy, control and perceived learnability with N=20, and that users of text-only LLM help often could not find the referenced UI and followed wrong advice verbatim — [arXiv 2504.15549](https://arxiv.org/abs/2504.15549); [arXiv 2402.08030](https://arxiv.org/abs/2402.08030)

### Inferences
- Claims the evidence does allow, phrased conservatively: (a) site-specific knowledge tends to improve which target the model picks, more so for smaller models; (b) LLM calls per task fall substantially only when a precomputed, executable path replaces intermediate calls; (c) such paths need tolerant element matching, per-step verification and a fallback; (d) the offline artifact costs minutes to hours of automated exploration plus some owner input, and needs upkeep per release.
- A human-in-the-loop guide differs from every evaluated system in ways that cut both directions: latency per step is felt directly and wrong pointers are visible (worse), but each step is verified by a human and followed by a fresh DOM (better), and real sessions generate demonstrations for free. None of these effects has been measured; they are my reasoning from the papers' mechanisms.
- The team's belief should be restated as a testable hypothesis: "with an interaction-level graph and per-goal path cache, at least X% of pointer steps can be served without an LLM call at Y% pointer accuracy". The literature gives reasons to expect X to be large on repeat goals (MobileGPT's 70–99% memory hit rates) but no number for help-widget traffic.

### Gaps
- No published study, as far as this search found, evaluates an embedded "show me where to click" assistant with offline site memory on speed, accuracy or user outcomes.
- No evidence on how a large static site map interacts with provider prompt caching and time-to-first-token in a one-call-per-step loop.
- Classic HCI findings on guided tutorials (speed, errors, retention) could not be verified in this session and should not be quoted with numbers until they are.
